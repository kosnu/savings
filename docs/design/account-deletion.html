「期限の1秒前 → 新しくログイン」と「期限ちょうど → 新しくログイン」を比べてください。締切後はAuthやデータがまだ残っていても取り消せません

猶予中は何が残る？

Authアカウント、本人の情報、家計簿への所属、家計簿のデータを保持します。本人のデータアクセスは利用停止にし、他メンバーは共有の家計簿を使い続けられます

物理削除で本人のAuth・登録情報・所属を削除します。他メンバーが残る家計簿とそのデータは保持し、誰もいなくなった家計簿は削除します

削除が遅れたり失敗したら？

期限後は処理待ちでも利用停止と取消不可を維持します。Authと関連データは同じトランザクションで削除し、途中の失敗は全体を元に戻します

失敗した要求は完了にせず次回以降のジョブで再試行します。運営者が失敗と処理の滞留を把握できるようにし、削除処理がcommitした後にだけ「完了」とします

実装で守る境界・記録を確認する

以下は設計の要点です。実装契約・権限・競合対策・検証条件の正本はアカウント削除設計書です。このHTMLは実際のOAuth、DBの認可、削除処理を実行しません

要求の状態 意味
pending 削除予約が有効。期限前は新しい本人ログインで取消可能。期限以後は取消不可のまま物理削除を待つ
cancelled 期限前に再有効化済み。削除予約は無効となり、通常利用に戻る
completed Authと関連データの物理削除がcommit済み
  • 有効なアカウント：Authとアプリ内ユーザーが存在し、pendingの削除要求がないこと。UIのログアウトだけでは停止を保証せず、保護されたデータのアクセスをDB側で拒否します。Authをbanする方式にはせず、本人の再ログインの入口を残します
  • 期限：DBのUTC時刻で申請から168時間。再有効化は現在時刻 < 期限のときだけ許可します。ログインとジョブが競合しても期限と要求の状態を同じ境界で再確認します
  • 再ログイン：本人が開始した新しいGoogleログインと対応する新規Authセッションを検証します。古いセッション・自動refresh・セッション復元だけでpendingを取り消しません
  • ジョブ：毎分期限を過ぎたpendingを処理します。Auth・関連データ・完了記録の更新を同じトランザクションで扱い、失敗時はpendingとデータを維持して再試行します
  • 状態確認：受付番号と確認キーで要求に限定した結果を確認します。申請の応答が途切れた場合は結果未確定とし、受付・取消・物理削除完了を推測で表示しません。確認キーにAuthトークンを流用しません
  • 最小の記録：取消・完了の記録を各確定時から30日保持し、期限後は照会不可として削除します。名前・メール・支払い・認証トークンはこの記録に残しません。受付番号・確認キーの紛失や記録の期限切れで照合情報が失われた場合、過去の完了を確定できないことがあります
  • 物理削除後：発行済みJWTが残っていても保護データへのアクセスを拒否します。バックアップや基盤ログには別の保持条件があり、すべての情報の即時消去は約束しません
