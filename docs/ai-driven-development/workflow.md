# AIDD v4

Intentに合う成果を、リポジトリのガードレールと実行証拠によって完成させる。
具体的な設計、作業順序、ツール、成果物、担当の分割はagentが選ぶ。
固定フェーズ、書類の数、特定モデルの手順を達成条件にしない。
[設計判断](../adr/0009-rebuild-aidd-v4.md)と[調査](research-v4.md)を根拠とする。

## Intentと実行権限

Intentは背景・目的・期待する成果・制約・観測可能な完了条件・委任範囲を伝える。
Issueでもユーザーの明示発言でもよい。開始時は出典の参照と本文、実行を依頼した発言をTaskに保存する。
以降のeventにはチャット本文を残さず、[Coreの記録契約](aidd-checker.md#記録)に従い出典・本文hashと構造化した判断を保存する。
説明・比較・調査だけの依頼を実装許可に読み替えない。通常の選択や範囲内の修正は追加承認なしで続ける。
開発作業の実行依頼では、[Git Workflowの開発の実行委任](../harness/policies/git-workflow.md#開発の実行委任)に従い、必要なブランチ作成から検証・レビュー後のPR作成または更新と配信確認までを通常の委任範囲とする。Issueの種別や依頼の入口によって、個別のブランチ・PR作成承認や別のShip指示を要求しない。ローカル完了などの明示制限があれば、開始時のIntentと実行権限に保持してその範囲を越えない。
目的、範囲、権限、成功条件を変える不明点だけを確認し、独立して進められる作業は継続する。

## サイクル

`Intent → 設計・実装・検証・レビュー → Ship → （手動開始）Audit → （改善提案がある場合）手動承認 → ガードレール改善 → Intentへ戻る`
を1サイクルとする。通常の実行委任はShipで終え、AuditはShip後にユーザーが明示的に依頼したときだけ開始する。改善後は現在のIntentと改善済みガードレールを読み直し、次のサイクルの設計・実装へ進む。
同じTask・baselineを維持し、Intentへ戻ることとIntent自体の改訂を区別する。
改善案がないAuditは報告で終了する。全案が明示却下された場合も改善・次サイクルを開始しない。

サイクルIDはTask内で一巡を識別する。新Task開始で最初のIDを発行し、改善後のIntent復帰で次のIDを発行する。
判断revisionの更新、再検証、同じShipへのAudit追記ではIDを変えない。
改善の実装は承認を得たサイクルに属し、Intent復帰後の設計・実装・検証・レビュー・Ship・Auditは次サイクルに属する。
これは固定executorや書類作成を要求するものではなく、承認と一巡の境界を追跡するための区分である。

CodexでのAIDD作業は、実際に行う工程の開始・終了で[セッション計測](aidd-checker-operations.md#セッション計測)を記録する。
各記録はセッション、Task ID、現行サイクルID、工程名を持つ。同じTask・サイクルが複数セッションにまたがっても、
セッションの切り替えをサイクル境界にしない。トークン使用量が取得できなければ不明として残し、推測しない。
計測結果は作業したセッションのメッセージでも返す。計測のために固定工程を増やさず、結果をPR本文・テンプレートへ載せない。
計測値は開発の証拠やShip gateではない。

## 開発のループ

現在のIntent、判断、未解決事項、証拠を読む。必要な文脈を取得し、設計・実装・観測・修正を繰り返す。
作業対象からrule-mapのpath/surface一致と依存closureを選び、該当本文を読んで適用する。
規則の存在や読了の自己申告だけで遵守を証明したとは扱わない。追加の意味的関連規則も判断する。

Taskは同じ成果の作業境界である。開始時baselineとIntentを保持し、設計・範囲・検証方法をdecisionへ記録する。
確定した判断を上書きせず、新revisionを追記する。checkpointは再開に必要な判断の境界であり、旧版の工程ではない。
改訂で旧証拠は失効する。失敗は実際の出力を調べて修正・再検証する。不明・不一致を合格へ丸めない。
新しい判断を要しない実装上の修正は、同じ判断の下で実施できるが、変更後の証拠が必要になる。

## 評価の責務

| 対象                                                                   | 担当と証拠                                                                             | 判断への接続                                         |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Intentへの適合、設計、ユーザーから見た動作、規則の意味                 | agentが具体的基準と観察・コード・テスト結果でレビュー。各条件をpass/fail/unknownで区別 | 不適合は修正。不足・矛盾は追加調査またはユーザー判断 |
| ファイル内容とmode、判断revision、検証の終了状態、証拠の鮮度、承認対象 | Go Coreが実データを照合                                                                | 不一致を拒否し、修正・再検証を要求                   |
| 意図の変更、Audit後の改善の許可                                        | ユーザーの明示判断と出典                                                               | 指定範囲だけに反映                                   |

ローカル検証は早期発見、GitHub CIはPRに対する最終的な検証を担う。CIの結果を確認してマージする運用と、
GitHubの必須チェックでマージを強制制限する機能は区別する。前者への合意から後者の設定変更を要求しない。
Task開始前のPR変更に対してローカル検証選択をさらに強制するGo検査は追加しない。
これは既存の必要なローカル検証や適用規則の確認を省略する指示ではない。

`go test`成功は仕様の妥当性を保証しない。reviewのpassもテスト実行の代替にならない。
意味評価は次の照合を既存のレビュー内で行う。別の承認段階や必須工程は設けない。

- 元のIntentとその出典、有効な既存の実行権限、最新の依頼・訂正を読み、ユーザーが求めた成果とagentが追加した判断を区別する。追加判断ごとに、目的の達成に必要な技術上の選択か、成果・公開先や公開範囲・権限・成功条件を変える選択かを、必要性と権限の根拠で評価する。agentの仕様やテストに書かれていること自体を根拠にしない。
- 期待結果は変更後の仕様から写すだけでなく、目的から保つべき性質を導く。たとえば同じ対象・連続した期間の累積増分なら、区間への分割で総量が欠けたり重複したりしないことを求める。観測条件や除外の根拠も確かめ、実際の出力・副作用・差分をその期待結果と照合する。仕様とテストが一致していても、目的に必要な結果が欠ければfailとする。
- 権限は最新の一文だけで判定せず、既存の承認の対象・条件と、最新依頼による限定・変更を照合する。返信のみという限定から編集権限を作らず、既に明示承認された同じ改善や通常の委任内の技術判断には追加承認を要求しない。範囲変更や権限の不明点が実際に残る部分だけを確認し、独立した許可済み作業は続ける。

reviewの根拠には、何を出典から期待し、実際に何を観測したか、その差と次の行動を残す。
不適合はfail、観測や権限の根拠不足はunknownとし、修正・追加調査・必要なユーザー判断へつなげる。
反例、失敗・空・境界条件、未確認事項を含め、[匿名化した適用事例](semantic-review-cases.md)のように判断と根拠を確認する。
独立評価者は重大リスクに効果がある場合に限る。
形式的な欄埋め、モデルの完了宣言、単一の総合点だけで成功にしない。

## Ship

Intentの成果が実装され、必要な検証と全適用規則のレビューが終わった時点で配信する。
[Git Workflow](../harness/policies/git-workflow.md)に従い、検証した内容・modeとstaged状態が一致することをGoで確認する。
stage範囲はTaskの担当差分に限定する。commit hook等が変更したら再検証する。
commit・push・PR作成または更新後、local HEAD、remote ref、tracking ref、upstream、PRのhead/baseをread-backする。
CI状態は一度取得し、未完了を成功扱いしない。merge/deployは別の権限である。
Ship結果と後からAuditを再開するためのTask参照・配信先・未確認事項を報告する。配信後のShip記録はTaskへ追記せず、レビューコメントの到着を自動で待機せず実行を終える。

## Auditと手動承認

Ship後にユーザーがAuditを明示的に依頼したら、[Audit policy](../harness/policies/learning-extraction.md)に従い、その時点で確認できる指摘とShipまでのセッションの開発プロセスを振り返る。
根拠、原因、改善案、対象を整理して提示する。解決済み指摘を未解決として復活させないが、
解決の過程で観測した再利用可能な問題は解決済みと明記して分析できる。
Audit中にガードレール・Intent等へ改善を適用しない。

改善提案がないAuditは結果を報告して終了し、Task記録を追加しない。改善提案がある場合は結果を提示して手動承認を待つ。開発の委任やShip許可を改善の承認として使わない。
ユーザーの明示承認を、具体的な提案と反映対象に結び付けて記録した後に着手する。
承認後も同じTaskで改善の判断を記録し、承認範囲のガードレール・Intentを改善する。
改善後は`return-intent`でIntentと改善済みガードレールの再確認を記録して次サイクルへ戻る。
その後、新decisionで設計・実装の要否と検証方法を判断し、検証・レビュー・Shipまで行う。次のAuditもユーザーの明示依頼で開始する。
次サイクルへ移っても承認範囲は拡張しない。必要な作業が範囲外なら追加の権限を確認する。
提案を変更した場合は旧承認で実施しない。却下・保留は実施完了と区別する。
改善事項がなければその根拠を報告し、追加の承認や記録を要求しない。
「Auditを承認します」は提示済み改善案の実行承認として扱い、別の実行承認段階を追加しない。方向性の指定だけを承認と扱わない。
追加指摘は同じShipの内容・判断revisionが変わっていない場合にAudit更新として追記し、旧Auditと承認は保持する。新Auditへ旧承認を流用しない。

## 継続と再開

同じ成果への修正・追加配信・承認された改善は同じTaskとbaselineを保持する。
別のIntentは新しい作業境界として扱い、Taskを作り直して未解決事項や古い証拠を隠さない。
再開時は[Core操作](aidd-checker-operations.md)でTaskと最新checkpoint、証拠の鮮度、承認待ちを確認する。
会話要約は案内であり、永続記録を再取得する。Goalの有無はCoreの検査を変えない。

## 完了

Ship完了と委任された実行の終了、Audit完了、改善承認待ち、承認済み改善の完了を別々に報告する。
成果・検証・レビュー・配信確認が揃っても、Audit未実施ならサイクル完了ではない。
改善案がある場合、承認待ちを成功や完了に変更しない。予算・時間切れも完了の根拠にしない。
