# Requirements: よくある支払いを入力候補として再利用できるようにする

## 1. 文書の位置づけ

- Initial input: GitHub Issue #1591
- Cycle ID: `d30893e2-55c4-4e11-8a6d-3f6eae8a94e4`
- Artifact lineage: `docs/ai-driven-development/workspaces/1591-frequent-payments-v2/`
- Related future work: GitHub Issue #1601

この文書は、Issue #1591と監督判断をRequirementsへ展開した正本である。前サイクルのRequirements、Design Doc、実装差分、UI挙動は入力として扱わない。

## 2. 背景

支払い登録では、繰り返し発生する同じ内容の支払いでも、メモ、金額、カテゴリを毎回入力する必要がある。

過去の登録内容を入力候補として再利用できれば入力負担を減らせる。一方、候補選択だけで支払いを登録すると、日付や今回だけ異なる内容を確認できない。候補は登録済み支払いではなく、確認・編集可能なフォーム入力として扱う必要がある。

## 3. 解決したい課題

- 最近繰り返し登録した支払いを、再利用する候補として素早く見つけられない。
- 同じメモでも金額またはカテゴリが異なる候補を、選択前に区別できないと誤入力につながる。
- 候補取得の失敗や再取得によって、既存の支払い作成を妨げてはいけない。
- データ構造とRLSは複数Book membershipを許容するが、現在のプロダクトではdefault Bookが唯一の操作対象である。候補も現在操作中のdefault Bookへ限定する必要がある。

## 4. 対象ユーザーと利用シーン

### 対象ユーザー

- 認証済みで、default Bookへ支払いを登録するユーザー。

### 利用シーン

- 支払い作成フォームを開き、過去1か月に繰り返し登録した支払いを再入力するとき。
- 候補の内容を今回の支払いに合わせて確認・編集してから登録するとき。
- 連続作成中に、新しく保存した支払いを含む最新候補を利用するとき。

## 5. ユーザーストーリー

- ユーザーとして、最近繰り返し登録した支払いを候補として見つけたい。そうすることで、再入力する内容を素早く選べる。
- ユーザーとして、同じメモの候補でも金額とカテゴリを見て区別したい。そうすることで、意図した候補を選べる。
- ユーザーとして、候補からメモ、金額、カテゴリを入力したい。そうすることで、毎回の入力負担を減らせる。
- ユーザーとして、候補選択後に内容を確認・編集してから登録したい。そうすることで、誤った内容の登録を防げる。
- ユーザーとして、候補がない、取得中、または取得失敗の場合も従来どおり支払いを作成したい。

## 6. スコープ

### 対象

- 現在のdefault Bookに属する支払いだけを対象にした候補抽出。
- 支払い作成フォームを開いた日を基準にしたrolling 1か月の期間。
- メモ、金額、カテゴリの完全一致による集計。
- 3件以上の候補を頻度降順で最大5件提示すること。
- メモを主ラベルとし、金額とカテゴリで候補を識別できる操作。
- 候補選択によるメモ、金額、カテゴリのフォーム値置換。
- loading、error、empty、送信中、連続作成、再取得の境界。

### 対象外

- 候補選択による支払いの自動登録。
- 支払い作成フォーム以外への候補表示。
- 候補の登録、固定、削除、並べ替え、表示件数設定。
- Bookの追加、選択、切り替え、共有、招待、メンバー管理。
- 支払いCRUD全体を選択中Bookへ統一する対応。これはIssue #1601で扱う。
- DB schema、API契約、RLS、認証、権限、新規依存の変更。
- 推薦学習、曖昧一致、近似金額、メモの正規化。

## 8. Domain Value Intent

| 値 | 利用目的 | UI上の扱い |
| --- | --- | --- |
| メモ | 候補の主対象を識別する | 候補の主ラベルとして保存値を表示する。空メモは候補から除外する。 |
| 金額 | 同じメモの候補を識別し、入力値を再利用する | 候補の補助情報として実値を表示し、選択時にフォームへ設定する。0円を未設定と混同しない。 |
| カテゴリ | 同じメモ・金額の候補を識別し、分類を再利用する | カテゴリ名またはカテゴリなしを補助情報として表示し、選択時にフォームへ設定する。 |
| 頻度 | 候補の優先順位を決める | 内部の順位付けに利用する。件数表示自体は要求しない。 |
| 支払い日 | 集計対象期間を判断する | `payment.date`をローカルdate-onlyとして期間判定に利用する。候補選択では変更しない。 |
| default Book ID | 現在操作中のBookを限定する | 候補取得条件として利用する。候補の表示値にはしない。 |
| フォーム現在値 | 今回登録する内容を確認・編集する | 候補選択で3項目だけ置換し、既存フォームをsource of truthとして扱う。 |

## 9. 用語と境界

### 現在の選択中Book

- 現在はBook追加・選択UIがないため、認証ユーザーのdefault Bookを現在の選択中Bookとして扱う。
- 候補集計はdefault Book IDで明示的に限定する。
- membershipはアクセス可能なBookの認可境界であり、今回操作するBookの選択境界ではない。
- 支払いCRUD全体に共通の選択中Book contextを導入しない。

### 直近1か月

- 支払い作成フォームを開いたローカル日付を基準日とする。
- 基準日の1か月前から基準日までを両端含みで扱う。
- 日付判定には`payment.date`を使い、`created_at`を使わない。
- 例: 基準日が2026-07-25なら、2026-06-25から2026-07-25までを含む。
- 月末に対応する日がない場合は、1か月前の月末へ丸める。
- 例: 基準日が2026-03-31なら、2026-02-28から2026-03-31までを含む。
- フォームを開いたまま日付が変わっても基準日は変更せず、次回フォームを開いたときに更新する。

### 同一候補

- 元の保存値であるメモ、金額、カテゴリIDの3値が完全一致する支払いを同じ候補として数える。
- メモをtrimまたは大小文字変換して同一視しない。
- カテゴリなし同士は同じ分類値として扱う。
- 同じメモでも金額またはカテゴリIDが異なれば別候補とする。

## 10. 機能要件

### FR-1: 対象期間の支払いを取得する

- 基準日から算出した開始日・終了日を両端含みで取得条件にする。
- 現在のdefault Book IDを取得条件にする。
- 期間またはBook境界外の支払いを候補集計へ含めない。

### FR-2: 完全一致で候補を集計する

- メモ、金額、カテゴリIDが完全一致する支払いを数える。
- `null`、空文字、空白のみのメモは候補から除外する。
- 金額0は有効な候補値として扱う。
- カテゴリなしは有効な候補値として扱う。

### FR-3: 頻度の高い候補を最大5件提示する

- 対象期間内に同一候補が3件以上ある場合だけ提示対象にする。
- 件数の多い順に並べる。
- 最大5件に制限する。
- 同件数の決定的な順序はDesign / Planで定義する。頻度の高い候補を低い候補より後にしてはいけない。
- 候補が1件以上ある場合だけ見出しと候補操作群を表示する。
- 候補が0件の場合、見出し、候補操作群、empty messageを表示しない。

### FR-4: 選択前に候補を識別できるようにする

- 各候補はbadge風のbuttonとして表示する。
- メモを視覚上の主ラベルとする。
- 金額とカテゴリ名またはカテゴリなしを、候補を区別するための補助情報として表示する。
- 同じメモの候補が複数あっても、金額とカテゴリを含めて選択前に区別できる。
- accessible nameにもメモ、金額、カテゴリを含める。
- 色、形、pointer操作だけに依存せず、buttonとして識別・キーボード操作できる。

### FR-5: 候補をフォームへ入力する

- 候補選択でメモ、金額、カテゴリの現在値を置き換える。
- 日付、連続作成設定、その他の既存状態を変更しない。
- 候補選択だけではvalidation submit、支払い作成、フォームcloseを行わない。
- 選択後もメモ、金額、カテゴリ、日付を確認・編集できる。

### FR-6: 候補機能が既存フォームを妨げない

- loading中、取得失敗、候補0件でも既存フォームを利用できる。
- 候補取得失敗を支払い作成失敗として扱わない。
- 候補領域に新しいerror messageまたは手動retry操作を追加しない。
- 一時的な取得失敗後、同じフォーム内で後続の再取得が成功した場合は候補を再表示できる。
- 支払い送信中は候補選択で送信値を変更できない。

### FR-7: 支払い作成後に保存済みデータから再評価する

- 支払い作成成功後、候補は保存済み支払いを基準に再取得・再集計する。
- 保存前の入力値を候補件数へ先行反映しない。
- 連続作成では、フォームreset後の値と最新候補を両立する。
- 通常作成でフォームが閉じた場合、次回フォームを開いたときに最新候補を利用できる。

## 11. 非機能要件と制約

- DB schema、API契約、RLS、認証、権限、新規依存を変更しない。
- default Bookの取得失敗をフォーム全体の失敗にしない。
- 候補は既存の主作成操作より弱い視覚的優先度にする。
- 候補を状態badgeや別のsubmit操作に見せない。
- メモ、金額、カテゴリの既存validationを候補値にも適用する。
- 最大5件に制限し、モバイルで既存フォームの読み順と操作密度を保つ。
- 候補queryは支払い作成成功後に最新化でき、Bookと期間の異なる結果を同じcacheとして扱わない。
- Issue #1601の共通選択中Book境界を先行実装しない。

## 12. 受け入れ条件

- AC-1: フォームを2026-07-25に開いた場合、2026-06-25から2026-07-25までの`payment.date`だけが候補集計に含まれる。
- AC-2: フォームを2026-03-31に開いた場合、開始日は2026-02-28となる。
- AC-3: 現在のdefault Bookと異なるBookの支払いは、他の値が一致していても候補件数に含まれない。
- AC-4: 同じ空でないメモ、金額、カテゴリの支払いが期間内に3件あると候補になり、2件以下では候補にならない。
- AC-5: 空または未入力として扱われるメモは、他の値が同じで3件以上あっても候補にならない。
- AC-6: 金額0とカテゴリなしは有効な候補値として集計される。
- AC-7: 候補は件数の多い順に最大5件表示される。
- AC-8: 同じメモで金額またはカテゴリが異なる別候補は、表示内容とaccessible nameの両方で区別できる。
- AC-9: 候補はpointerとkeyboardの両方で選択できるbuttonである。
- AC-10: 候補選択でメモ、金額、カテゴリだけが置き換わり、日付は変わらず、支払いは作成されず、フォームは閉じない。
- AC-11: 候補選択後の値を既存フォームで編集できる。
- AC-12: 候補0件、loading中、取得失敗時は候補領域を表示せず、既存フォームで作成・キャンセルできる。
- AC-13: 一時的な取得失敗後に再取得が成功すると、同じフォーム内で候補を再表示できる。
- AC-14: 支払い送信中は候補選択で送信値を変更できない。
- AC-15: 連続作成で支払いが成功すると、保存済み支払いを含めて候補が再評価され、フォームreset後に未保存入力が残らない。
- AC-16: 候補機能のためにDB schema、API契約、RLS、認証、権限、新規依存を変更しない。

## 13. Q&Aログ

- Q: 複数Book membershipを考慮してBook選択機能を追加するか？
  - A: しない。現在はdefault Bookが唯一の操作対象であり、共通の選択中Book境界はIssue #1601で扱う。
- Q: 候補取得をBook filterなしでRLSだけに任せるか？
  - A: 任せない。membership認可と今回の操作対象を分け、default Book IDで明示的に限定する。
- Q: メモが同じ別候補をどう区別するか？
  - A: メモを主ラベルに保ち、金額とカテゴリを補助情報およびaccessible nameに含める。
- Q: メモ未入力の支払いも候補にするか？
  - A: しない。候補の主ラベルと識別対象が成立しないため除外する。
- Q: カテゴリなしの支払いは候補にするか？
  - A: する。カテゴリは任意であり、カテゴリなしを有効な分類値として扱う。
- Q: 取得失敗時にretry buttonを追加するか？
  - A: 追加しない。フォームを妨げず非表示にし、後続の自動再取得成功時に復帰できるようにする。
- Q: 候補選択で入力済みの値はどうなるか？
  - A: メモ、金額、カテゴリは候補値で置き換える。日付と連続作成設定は維持し、選択後に編集できる。

## 14. 技術的考慮事項

- default Bookの取得と候補取得の接続方法はDesign / Planで決定する。
- Book ID、開始日、終了日が異なる候補結果をcache上で区別する必要がある。
- default Book取得または候補取得の失敗を、親フォームのSuspense/error境界へ伝播させない。
- responseの妥当性を検証し、取得失敗と候補0件を同じデータ状態へ変換しない。
- 候補の集計と決定的なtie-breakerは、UI表示から分離して検証可能にする。
- 連続作成では、保存成功、query invalidation、再取得、フォームresetの順序と接続を検証する。

## 16. Stop条件

- default Bookへの明示的な絞り込みにDB、API、RLS、認証、権限変更が必要になる。
- 候補を識別するために新しい画面遷移、確認操作、候補管理が必要になる。
- Issue #1601の支払いCRUD全体対応が必要になる。
- 既存フォームの主要操作または支払い仕様を変更する必要がある。
- 新規依存またはスコープ外変更が必要になる。
