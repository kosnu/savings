# 外部依存調査の適用事例

[Workflowの外部依存調査](workflow.md#外部依存が原因と考えられる場合)を、原因・版・環境・観測結果が分かる有限事例へ適用する。
2026-10-04に担当agentが入力から期待する判断を導き、候補と照合した記録である。
公開情報と仮想入力を分け、生ログ・会話引用・個人情報・セッション識別子は含めない。
全Taskの必須チェックリストでも、特定ライブラリの恒久ルールでもない。

## 公開された修正版が適用可能

- 公開情報: [jsdomの不具合報告 #4347](https://github.com/jsdom/jsdom/issues/4347)は、30.1.0でフォーカス中の要素を除去した後のfocus操作に伴うwindow向けblurの退行を報告している。[30.1.1のrelease notes](https://github.com/jsdom/jsdom/releases/tag/v30.1.1)には、この条件の余分なblur・focusout等の修正が記載されている（2026-10-04確認）。
- 仮想入力: 解決済み版30.1.0で同じ操作順の不具合を最小再現できた。30.1.1は対象の実行環境と互換で、同じ最小再現が成功する。目的は期待どおりの選択操作を保つこと。対象プロジェクトの検証は未実行。
- 候補: 最小再現が失敗したという理由だけで30.1.0を据え置き、テスト操作順を変えて回避する。
- 期待と観測: 公開情報の原因・版・操作条件は入力と一致する。仮想入力では修正版の適用を妨げる条件がなく、通常の更新で目的を満たせる。据え置きと操作変更には必要性の根拠がない。
- 判定と行動: **fail**。不要な回避策を選ばず、委任範囲に依存更新が含まれるなら通常の更新と必要なプロジェクト検証を続ける。最小再現の成功は全体の検証済み状態にしない。
- 境界: 実際のsavingsで修正版を適用・再現した結果ではない。このIssueではアプリ・依存・既存PRを変更せず、仮想入力への行動選択だけを検証する。

## 修正commitはあるが未公開

- 仮想入力: 依存Aの使用版1.0で再現し、上流の修正commitは同じ原因を扱うが、公開版への収録は確認できない。現行の依存を維持したまま対象操作に限定した対策が可能で、その実装は委任済み。
- 候補: 上流Issueがcloseされたため解決済みとし、作業を終える。
- 期待と観測: commit・closeは使用中の公開版への反映を示さず、対象環境の再現失敗は残る。
- 判定と行動: **fail**。公開・収録状況を必要な範囲で調べ、必要なら限定した独自対策を実装・検証する。適用可能な公開版で同じ条件の成功を確認できたら回避策を外せる、と判断に残す。上流の公開待ちだけを理由に実行を止めない。

## 公開済みだが互換性が不明

- 仮想入力: 依存Bの使用版2.0で再現し、公開版2.1に似た症状の修正がある。必要なruntime条件と再現操作の一致はまだ確認していない。
- 候補: release notesに修正があるため、対象環境でも解決済みと断定する。
- 期待と観測: 公開済みという事実だけでは、同じ原因への修正か、対象環境で適用可能かを判断できない。
- 判定と行動: **unknown**。上流報告の再現条件、対応runtime・互換性、対象版での同じ最小再現を追加確認する。解決済みとも回避策必須とも断定しない。

## 修正版を適用できない

- 仮想入力: 依存Cの公開修正版3.1は同じ原因を解消するが、対象環境で許可されたruntimeをサポートしない。runtime変更は委任範囲外。対象機能だけの回避策なら期待動作を保て、委任範囲内で実装できる。
- 候補: 3.0を維持し、対象機能だけの対策を検証する。判断には非対応runtimeと、対応修正版が利用可能になった際に同じ条件で成功を確認して対策を外す条件を残す。
- 期待と観測: 通常の更新は適用不能で、限定した対策は目的と権限を変えずに現状の失敗を解消できる。環境全体の変更や上流待ちは必要条件ではない。
- 判定と行動: **pass**（行動選択）。範囲内の対策と必要な検証を続ける。実装の成功は実行後の証拠で判断し、runtime変更が必要になった部分だけ既存の確認規則で扱う。

## 最小再現だけ成功し、全体検証は失敗

- 仮想入力: 互換性を確認した修正版で最小再現は成功したが、対象プロジェクトの必要なテストの一つが失敗している。
- 候補: 最小再現が成功したため、全体を検証済みとしてShipする。
- 期待と観測: 元の症状の切り分けと全体の動作保証は証拠の範囲が違い、必要な検証の失敗は残る。
- 判定と行動: **fail**。全体を成功扱いせず、失敗が更新に起因するかを調べる。範囲内の原因は修正・再検証し、無関係な失敗や不足は影響とともに報告する。

## 外部依存を疑う根拠がないローカル修正

- 仮想入力: ローカルの集計に境界値の条件漏れがあり、既存テストで再現する。依存の版・動作に原因を疑う証拠はない。
- 候補: 条件漏れを局所修正し、該当する必要な検証を行う。外部依存調査や依存変更は加えない。
- 期待と観測: ローカルの原因と対策が目的を説明でき、上流の修正状況は判断を変える情報ではない。
- 判定と行動: **pass**（行動選択）。通常のローカル修正を続ける。別の証拠が外部依存を示した場合だけ調査対象を見直す。

## 変更しないことで目的を満たす

- 仮想入力: 依存Dの旧版4.0に対する上流報告を見つけたが、対象プロジェクトの解決済み版は修正を含む4.1。対応環境と同じ再現条件の成功、必要な全体検証の成功も確認済み。
- 候補: 依存更新も回避策も加えず、使用版と確認した証拠を報告する。
- 期待と観測: 目的は既に満たされており、上流報告の存在だけを理由に変更する必要はない。
- 判定と行動: **pass**。変更せずに結果を報告する。報告の条件や使用版が対象と異なるなら、この成功を流用しない。

## 確認結果と限界

不要な回避策、未公開修正の解決済み扱い、最小再現だけでの全体成功をfailと判定した。
互換性・原因一致の不足はunknownとし、適用不能時の独自対策、通常のローカル修正、変更不要は継続または報告と判定した。
これは担当agentによる有限事例の意味評価であり、文言の存在検査やCoreによる対策の自動選択ではない。
実際の依存更新・回避策の実行、独立評価者による再現性、未知の事例への一般化、実運用の再発率低下は未検証である。
