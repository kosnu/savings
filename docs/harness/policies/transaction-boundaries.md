# Transaction Boundaries

1つのユーザー操作が複数のデータ作成・更新・削除を含む場合は、片方だけ成功した状態がユーザー体験やデータ整合性を壊さないかを確認します。

片成功を避ける必要がある場合は、Design / Planで同一操作単位を明示します。実装手段は既存構成と制約に合わせて選びます。

## 判断基準

次のいずれかに当てはまる場合は、同一操作単位として扱うことを検討します。

- 片方だけ成功すると、ユーザーに成功状態を誤認させる
- 片方だけ成功すると、後続画面や集計結果が要件と矛盾する
- ユーザーが1つの保存・作成・削除操作として認識する
- 失敗時に個別復旧よりも全体失敗として扱う方が自然
- 片成功の検知や補償処理が複雑になる

## Design / Planで決めること

- どのデータ変更を同一操作単位に含めるか
- 期間や履歴を持つデータでは、対象月や対象日を決める入力を同一操作単位に含めるか
- どの層で境界を作るか
- 操作の実行境界と、入力値へ適用するルールの所有境界をどの層が担うか
- 片成功が起きた場合のユーザー影響
- 採用しない案と理由
- 残る競合リスクやスコープ外の補償

## Write後の確認失敗

source of truthへのwriteと、その結果を確認するread-backまたはrefetchは、別の成功・失敗境界として扱います。writeが成功した後に確認だけが失敗した状態をwrite失敗とみなし、write前の値へ戻したように見せてはいけません。source of truthには新しい値が残っている可能性があるためです。

Design / Planでは、少なくとも次の状態を区別し、それぞれの遷移とユーザーへの伝え方を定義します。

- write失敗
- write成功・確認失敗
- write成功・確認成功

write成功・確認失敗では、再確認のretry、source of truthへの収束、または明示的な補償のどれを行うかを決めます。client-side cacheや画面上の値だけを以前の状態へ戻して、source of truthも戻ったと推測してはいけません。

write成功・確認失敗は、確認成功または明示的な補償の完了まで、未確認の結果として扱います。この結果は、そのユーザー操作の完了を所有する境界から観測できなければなりません。確認失敗を握り潰すことや、完了を所有する境界が参照しないerror stateにだけ保持することを、失敗処理の完了としてはいけません。

再試行では、原則として確認のread-backまたはrefetchを実行します。成功済みのwriteは、冪等性が保証され、その再実行を明示的に採用している場合を除き、自動で繰り返してはいけません。自動再確認によって収束できる場合は、確認失敗を直ちにユーザー操作へ要求する必要はありません。未確認の結果が残り、ユーザー操作が必要な場合は、その状態と再確認の経路をユーザーへ伝えます。

検証では、writeが重複して実行されないこと、確認失敗をユーザー操作全体の成功またはwrite失敗として確定しないこと、再試行が採用した確認処理を実行すること、および確認成功または明示的な補償へ収束できることを確認します。

## 実行境界とルール所有境界

操作の原子性を保証する実行境界と、validation、正規化、上限、既定値などのルール所有境界は分けて判断します。

RPCやdatabase functionを実行境界に選んでも、その操作に関わるすべてのルールをDBが所有することにはなりません。ルールを配置する層は、その実行手段ではなく、ルールを守る理由と適用範囲で決めます。

- 呼び出し元に関係なく守る必要があり、データ整合性、参照整合性、認証、権限、または原子性を保護するルールは、APIまたはDBの境界で保証します。
- 特定のアプリケーションやユーザー体験に固有で、保存層がより広い値を正しく保持できる入力制約、正規化、上限、既定値は、そのアプリケーション層が所有します。
- アプリケーション層が所有する値ルールは、適用後の値をRPCやAPIへ明示的な入力として渡します。RPCやDB側で同じルールを再定義しません。
- 実行境界を選ぶ都合だけでルール所有境界を移す必要がある場合は、Design / Planで理由と影響範囲を明示します。根拠をRequirementsまたは正本ルールへ追跡できない場合はStopします。

## 実装境界の候補

- DB transaction / database function
- RPC / API endpoint
- アプリケーション層の明示的な更新順序と失敗処理
- 補償処理または再試行

DB constraint、trigger、RPC、API追加などが既存の制約やスコープを超える場合は、Build / Verifyで勝手に追加せずStop条件として扱います。

時系列状態を保存する操作では、DB側の現在日時で対象期間を補完して、read側とwrite側の期間基準を分離しないようにします。
