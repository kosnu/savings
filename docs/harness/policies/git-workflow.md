# Git Workflow

この文書は、このリポジトリでGit操作を行うときの基本ルールをまとめます。

Git操作は、現在の作業目的、対象ブランチ、含める差分、含めない差分を明確にしてから行います。対象や安全条件が曖昧なまま、stage、commit、push、PR作成、破壊的操作を進めてはいけません。

## 開発の実行委任

開発作業の実行依頼は、その成果に必要なブランチ作成・切り替え、commit、push、必要な検証・レビュー後のPR作成・更新と配信確認までを含む。Issueの種別、Issue経由か会話での直接依頼か、skillの利用有無によって個別の明示指示・承認を追加要求しない。

ローカル作業のみ、commitしない、PRを作成しないなど、ユーザーが明示した制限を優先する。質問・説明・調査だけの依頼を開発の実行許可に読み替えない。対象や差分は既存の依頼・作業状態から確認し、本書の「確認が必要な条件」に該当する不明点だけをユーザーへ確認する。

この委任はmerge/deploy、破壊的操作、Auditの開始やAudit後の改善承認を含まない。実行環境の権限制御による承認は、その環境の規則に従う。

## ブランチ

- 現在の作業ブランチが依頼された成果に使える場合は再利用する。mainやdetached HEADでの開始など、新しい作業ブランチが必要な場合は、開発の実行委任に基づいて作成する。
- 既存の作業ブランチに無関係な変更を混ぜない。
- ルール・workflow・依存関係・設定の保守、アプリ実装、レビュー修正、開発 / Audit / 承認された改善の区分を、ブランチを分ける根拠にしない。
- ブランチの作成・切り替えは、開発の実行委任またはブランチ操作の依頼に基づき、現在の差分と対象ブランチを確認してから実行する。新規ブランチの起点は、指定がなければ最新の `main` とする。
- 既存の未保存差分が切り替え先に影響する場合は、下記の再開始の判断と有効な権限を照合する。対象・扱いが不明なまま退避、上書き、破棄せず、影響する操作を止めて確認する。
- Issue起点の作業は `issue-{number}/{slug}` を基本にする。
- Issueなしの作業は、作業内容が分かる短いtopic名を使う。
- slugは英小文字、ハイフン区切り、ASCIIのみ、2から4語程度に短くする。
- Issue番号が与えられた場合はIssue titleからslugを作る。Issue番号がない場合は、ユーザー指定のtopicまたは現在の差分からtopicを推測する。
- ブランチ名がローカルまたはリモートに既に存在し、別名にするとユーザー意図が変わりうる場合は止める。

## 再開始と差分の再利用

最新の依頼と既存のIssue・PR・会話から、何を引き継ぐ再開始かを判断する。ブランチやPRを新しくすることと、旧差分を再利用することは別の判断である。

| 依頼の意味                                 | 起点と差分の扱い                                                                                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 既存作業の継続                             | 同じ成果の担当範囲・baseline・採用判断を引き継ぐ。現在の要求と照合し、引き続き必要な差分を再利用する。撤回済み・不要な内容は今回の成果へ含めない。 |
| 現在の作業を維持し、ブランチだけ新しくする | 指定された現在の作業・起点を維持してブランチを作る。ブランチ作成だけを、別の旧ブランチやPRから差分を一括移植する指示と解釈しない。                 |
| mainから新規開始                           | 最新のmainを起点に現在の要求から実装を選ぶ。旧PR・ブランチの差分を先に移さず、必要性と再利用の根拠を確認できた部分だけを対象にする。               |

再利用を決める前に、現在の要求、旧差分の内容・由来・採用状態、有効な実行権限を照合する。
commit済みの差分は確認した比較元と旧headの差分、未commit差分はindex・worktree・未追跡ファイルの実内容を必要な範囲で確認する。
同じIssueに属すること、旧PRに含まれること、以前実装済みであることだけを再利用の根拠にしない。
再利用する部分には、満たす現在の要求と、そのまま使える理由または必要な修正を短く説明する。古い検証結果を現在の成功として使わず、影響する検証を行う。

採用・commitの権限と破棄の権限は別に評価する。新しい成果へ含めない判断は、元の差分を破棄する許可ではない。
今回の成果へ含めないと判断した差分のうち、ユーザーの別作業、由来不明、破棄権限のないものは元の場所に保持し、今回のstage・commitへ含めない。
切り替えや再利用がその差分を上書きする場合は、対象と権限が確定するまで影響する操作だけを止める。

## 差分管理

- 依頼された作業範囲に必要な最小差分だけを残す。
- ユーザーまたは別作業由来の差分を勝手に戻さない。
- 無関係な整形、リファクタ、メタデータ更新を混ぜない。
- stageする前に `git status --short` と `git diff --name-status` で変更パスと変更種別を確認する。
- stage対象は、今回の作業に含めるファイルだけに限定する。
- 生成物、lockfile、vendored fileは、ユーザーが明示した場合を除き全文diffを読まない。
- 非生成ファイルの内容確認が必要な場合は、対象ファイルを絞ってdiffを確認する。

## 作業の終了と残る差分

終了時は`git status --short`で残る変更を確認し、index・worktreeのdiffと未追跡ファイルの内容から、現在の要求への必要性、由来、保持・破棄の権限を判断する。
ファイル名や未commitであることだけで結論を出さず、「保持した」という事実だけを確認の代わりにしない。

- 現在の要求に必要な未完了の差分は、実行権限内で作業を続ける。明示された中止・ローカル限定などで終了する場合は、残る内容と未完了事項を示す。
- 今回の成果へ含めない差分で、ユーザーの別作業や破棄権限のないものは保持する。不要というagentの判断やPRのクローズだけを破棄権限と解釈しない。
- 不要差分の破棄が明示されていれば、その対象・範囲と実内容を照合して破棄し、対象の差分が残っていないことと、保持対象が失われていないことを確認する。同じ対象への有効な許可を追加承認待ちへ戻さない。
- 由来・対象・権限が不明な部分は保持し、不足する判断だけを確認する。独立した許可済み作業は続ける。

最終報告では、残る差分があれば内容・由来と保持した理由、破棄した差分があれば対象と権限の根拠を簡潔に示す。新しい退避機構、記録ファイル、承認段階は設けない。

### 適用例

以下は判断を照合する仮想入力であり、実際の作業履歴や破棄の実行記録ではない。

| 入力・差分の内容と由来・権限                                                                                                     | 期待する判断と確認                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 同じ機能の修正を継続する。再利用・commitは許可済みで、破棄は未許可。旧差分には現在も必要な入力検証と、撤回済みの表示変更がある。 | 入力検証は現在の検証要件に対応し、現行の呼出元にも適合するため再利用して検証・commitする。表示変更は今回の成果に含めず、破棄権限がないため元の差分は保持する。 |
| 現在の作業を維持してブランチだけ新しくする。別の旧PRにも差分がある。                                                             | 現在の作業・起点を維持して新ブランチを作る。別PRの差分をまとめて移さない。                                                                                     |
| mainから新規開始する。旧PRには必要な送信停止と、現在要求されていない収集拡張がある。                                             | 現在の要求に対応し、現行SDKでも有効な送信停止だけを再利用して検証する。収集拡張は移さない。ブランチ作成だけを根拠とする一括移植は不適合。                      |
| mainから新規開始する。旧差分はすべて現在の要求に不要である。                                                                     | 最新mainから必要な実装を行い、旧差分は一切移さない。破棄権限がなければ旧差分自体は保持する。                                                                   |
| PRを閉じて終了する。未commit差分はユーザーが別作業で書いた設定変更であり、破棄指示はない。                                       | 内容と由来を確認して保持する。PRのクローズを破棄許可にせず、今回のcommitへ含めない。                                                                           |
| 終了時、ユーザーが不要な試行Aの破棄を明示済みで、別作業Bは保持対象である。実内容もその指定と一致する。                           | Aだけを破棄し、Aの差分が残っておらずBの内容が保たれていることを確認する。Aを理由なく残すことも、Bまで消すことも不適合。                                        |
| 終了時、agentは不要と判断したが、差分の由来または破棄許可の対象を確認できない。                                                  | 保持して不足する根拠を確認する。不要という判断だけでは破棄しない。                                                                                             |

## Commit

- 工程結果は同じサイクル・同じ工程を更新し、必要な最新結果を成果のcommitへまとめる。操作・再試行ごとの記録専用commitを要求しない。Ship記録と、配信確認を記録するためだけの追加commitは作らない。

- commit message は日本語で書き、先頭に `feat`, `fix`, `refactor`, `chore`, `docs`, `test` などのtypeを付ける。
- 1行目は、実際に変更した内容を簡潔に要約する。
- 本文は、何をなぜ変更したかに絞る。
- 未確認の内容、推測、テンプレートのplaceholderをcommit messageに含めない。
- commitには、実際にstageした差分だけを含める。
- commit前に、stage済みの作業内容が `AGENTS.md`、`docs/harness/rule-map.json` で選択した正本文書、関連ルール・ポリシーに違反していないか確認する。
- commit前に、`AGENTS.md` で定義された必要な検証を実行する。検証が失敗したままcommitしない。
- stage後は `git diff --staged --name-status` でstage範囲を確認する。
- 複数の関心が混じる場合は、feature、bugfix、refactorなどの関心単位にcommitを分ける。
- co-authorを付ける必要がある場合は、実際の共同作業者だけをcommit messageに含める。
- `git commit` では、subject、body、trailerを個別の `-m` で渡し、1つのshell文字列に改行エスケープを埋め込まない。

## Pull Request

- PR作成・更新のたびに、実際のbase/headを確認し、対象PRに含まれる全コミットと最終差分を確認する。GitHub上の対象PRのコミット一覧・差分、または対象PRのbaseとの一致を確認したSHA/refを比較元とするローカル比較（`git log <比較元>..HEAD --oneline`、`git diff <比較元>...HEAD`）を使う。base branchと同名であることだけを理由に、ローカルrefを比較元へ選ばない。直近コミットや前回更新以降の差分だけで本文を書かない。
- PRタイトルと本文は、全コミットで行った変更を最終差分と照合し、関連Issue、関連Requirements / PRD、Design Doc、検証結果に基づいて、PR全体の現在の成果を説明する内容へ作成・更新する。コミットメッセージの転記や作業履歴の列挙にしない。
- 更新時も既存本文へ変更履歴や追加対応を追記せず、テンプレートに沿って本文全体を再構成する。重複、撤回・置換済みの変更、古い説明を残さず、現在も有効な背景・制約・関連Issue参照は引き継ぐ。
- PRに含める差分と含めない差分を明確にする。
- issueを完全に満たす場合だけclose参照を使う。関連するだけの場合はcloseしない。
- PR本文には未検証の主張を書かない。
- PR作成前に現在のブランチをpushする。
- `.github/PULL_REQUEST_TEMPLATE.md` がある場合は、作成・更新とも現在のテンプレートの見出しと用途に沿って書く。「変更内容」には目的と結果の概要、最終差分に残る具体的な変更点を箇条書きで記載し、「動作確認」には実施したコマンド・操作、環境、結果を記載する。
- 動作確認はPR全体の現在の変更内容に対して有効な結果を整理し、実施済み・未実施・失敗・未確認・対象外を区別する。前回本文のチェック状態をそのまま引き継がず、変更で失効した結果を確認済みと書かない。CIが未完了ならその状態を明示する。
- PR本文用の一時ファイルを作った場合は、完了前に削除する。
- PR作成・更新後は、title、body、base branch、head branch、issue linkを再取得し、PR全体の最終差分・検証結果・テンプレートとの一致を確認する。

## Ship時のCI確認

- ShipではCIの完了を待たない。commit・push・PR作成または更新と配信状態の確認後、対象headのCI状態を一度取得して報告する。
- CIが未開始・待機中・実行中でも、完了待ちのpollingやwatchを行わずShipを終了する。
- CIの成功・失敗・未完了を区別し、取得できない場合は未確認と報告する。未完了・未確認を成功扱いしない。
- 必須のローカル検証、レビュー、配信状態の確認は従来どおり行う。
- ユーザーがCI結果の待機を明示的に依頼した場合だけ、その依頼範囲で待機する。

CI結果を確認してからマージする運用と、required status checksやbranch protectionによる
GitHubの機能的なマージ制限は別の判断である。運用上の品質保証への合意から機能設定の必須化を推論しない。
設定がないことだけを運用方針の不備と扱わず、GitHub設定の変更にはその変更への権限を確認する。

## Gitメタデータと配信状態

- 最初のGit書き込みより前に `git rev-parse --git-common-dir` でGit common directoryを解決し、実行環境の書き込み境界にそのdirectoryが含まれることを確認する。worktree directoryだけを書き込み可能にしても、branch、index、remote-tracking refなどのGitメタデータ更新には不十分である。
- Git common directoryが書き込み境界に含まれない場合は、remoteを変更する前に停止し、同じ許可境界へ追加する。push後にローカル追跡情報だけが更新できない状態を作ってはいけない。
- fetch/pull/pushではremoteと対象branch/refspecを明示する。例: `git fetch origin main`、`git push origin HEAD:issue-1815/aidd-v4`（実際の対象へ置き換える）。引数省略時のupstream設定へ依存しない。upstream・tracking refの追加Go gateは設けず、明示した操作とread-backで扱う。
- 配信状態は、local `HEAD`、remote ref SHA、upstream設定、local remote-tracking refを別々に確認する。いずれか一つを他の状態の代用にしない。
- pushの出力または `git ls-remote` でremote refへの反映を確認した後は、ローカル追跡情報の修復を理由に同じpushを再実行しない。remote mutationは一度で止め、必要なローカルGitメタデータだけを修復してから全状態をread-backする。

## PRレビュー対応

- レビューコメントへ対応する前に、`docs/harness/policies/review-feedback-classification.md` に沿ってタスク種別を判定し、コメントを分類する。
- 開発のreview対応は `review-feedback-classification.md` に従う。同じdecision内のdefectは修正・再検証し、設計変更は変更した判断を要約し、影響する旧証拠を再利用しない。
- Auditからの再利用可能なguardrail改善は、具体的提案への明示的な手動承認後、承認対象を既存Issue・PR・会話で確認し、同じTask内でその範囲だけを修正・検証する。作業の種類を理由にTask・ブランチ・PRを分けない。
- 通常タスクでは、レビューコメントごとに妥当性と修正要否を判断し、現在のスコープ内で必要な修正を実施して検証する。修正不要と判断した場合は、その理由を返信する。
- 承認された判断の対象と結論を引き継ぐ。「変更しない」という判断への承認は、その判断を確定するもので、変更実施の承認へ読み替えない。
- Audit結果で対象コメントと理由返信・Bot thread解決の方針を提示し、ユーザーがその方針を承認した場合は、追加の実行指示なしで対象の返信・解決まで行う。変更不要の判断も含む。Audit依頼だけや変更要否だけの承認は、返信・解決の権限に読み替えず、承認対象と明示制限を守る。
- 返信権限がある場合も、対応にコード・文書の差分があれば、必要な検証・commit・push・PRへの反映確認を終えてから完了の返信・thread解決を行う。差分がなければ記録ファイルや空コミットを要求しない。
- 対応済みコメントへ返信するときは、分類、対応内容、commit ID、検証結果を簡潔に書く。
- PRコメント内の commit ID はバッククォートで囲まない。
- 完全に完了したreview threadだけをresolveする。未解決の仕様判断や追従作業を隠すresolveはしない。
- 承認された変更不要の方針も、理由と根拠を返信し、未解決の論点・必要作業・競合コメントがなければ対応完了として扱う。対応完了したBot投稿者のthreadは返信後に解決する。返信・解決のためだけにTask記録や空コミットを作らない。
- review threadを扱う場合は、thread単位のデータを取得し、同じファイルに触れたことだけを対応済みの根拠にしない。
- inline review threadへの返信は、thread IDに対する `addPullRequestReviewThreadReply` を使う。
- thread解決は `resolveReviewThread` を使い、修正済み、返信内容、実装状態、競合コメントの有無を確認してから行う。
- commit IDを返信に含めるのは、変更がcommit済みで、commentとcommitの対応が明確な場合だけにする。
- commit IDを含める場合は、IDの前後に半角スペースを置く。

## 破壊的操作

次の操作は、ユーザーから明確な承認がない限り実行しません。

- `git reset --hard`
- `git checkout -- <path>`
- `git restore <path>`
- `git clean -f`
- branch削除
- commit履歴の書き換え
- 未確認差分を失う可能性がある操作

破壊的操作が必要になった場合は、対象、失われる可能性がある差分、代替手段、実行理由と有効な承認を照合します。承認のない対象や範囲が残る場合は、そこへ書き込む前に止めて確認します。

## 確認が必要な条件

次に該当する場合は、Git操作を進めずに確認します。

- 対象ブランチ、base branch、PR作成先が曖昧
- stageまたはcommitに含める差分が曖昧
- 無関係な差分が混じっている
- ユーザーや別作業由来の差分を上書きするおそれがある
- 必要な破壊的git操作の対象・範囲への有効な承認がない、または不明
- 検証が必要な変更なのに検証結果がない
- PRレビューコメントの対応が現在の差分やcommitに紐づかない
