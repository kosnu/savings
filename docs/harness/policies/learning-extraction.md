# Auditとガードレール改善

[AIDD v4](../../ai-driven-development/workflow.md)のShip後の指摘分析を扱う。
Auditは分析であり、改善の実行権限ではない。旧Learnという一体の工程は使用しない。
作業過程全体の振り返りは、Merge / Close後の[Retrospective](retrospective.md)が扱う。

## Audit

AuditはShip後のユーザーの明示依頼で開始する。Ship直後の実行委任から自動で開始せず、後から届くPRレビューコメントをShip時点に存在したものとして扱わない。
対象の明示指定があれば、その指定を優先する。対象未指定なら、既存Issue・PR・会話から現在の作業Taskと配信対象PRを特定し、維持する。
直前に別Issueを編集しただけでは、そのIssueへAudit対象を切り替えない。
PRが候補なら、最新のPRコメント・レビュー指摘・threadごとの解決状態を取得してから分析対象を確定する。
たとえば「PR作業 → 説明用HTMLの作成 → Audit」でも、直前の成果物だけを根拠にHTMLを対象にしない。
「このHTMLをAudit」のような明示指定では、その成果物を対象にする。取得不能や複数候補で対象が定まらない場合は、不足する情報を示して必要な確認を行う。
指摘がない場合はその事実を報告し、作業過程の改善探索に切り替えない。

レビュー指摘や成果へのユーザーの訂正を、実際の記録に基づいて確認する。
指摘の原因を確かめるために関連する作業記録を参照できるが、進め方全体の改善探索へ広げない。
PR threadを入力にする場合はthreadごとの
解決状態とコメントを確認し、解決済みの問題を未解決扱いしない。
解決過程の一般化できる問題は、その解決状態と分析の目的を区別して扱える。

各改善候補には観測事実・出典、影響、原因または原因未確定、具体的改善案、有限の反映対象、
改善後の確認方法を示す。
原因分析では、症状（観測された不具合と影響）、発生原因（その不具合を生じさせた要因）、
見逃した理由（検証・レビュー等で検出できなかった要因）、直接修正（対象の不具合を解消する変更）、
根本対策（発生・見逃しの原因に対する再発防止）を分ける。症状の言い換えを原因とせず、
直接修正ができることだけで根本対策も確定したと扱わない。
発生原因と見逃した理由にはそれぞれ根拠となる記録・差分・検証結果等の出典を示す。
不明な項目は原因未確定とし、不足する根拠と追加で確認する対象を明示する。
方針不足、索引の到達性、読込・適用漏れ、検出漏れ、局所的な誤りを区別する。
既存規則があるだけで適用できたとは扱わず、推測した原因から禁止事項を増やさない。

原因分析では、案件固有のIntentの十分性と、共通ガードレールの改善要否を独立して判断する。
共通ルールの追加・変更が不要という理由だけで、Intentの修正も不要とは判断しない。
IntentはIssue本文とユーザー発言・訂正の出典を照合する。求める成果・制約・完了条件の不足や、
訂正が次の実行で参照するIntentに未反映のため別セッションで同じ誤りを繰り返す余地がある場合は、
不足する要件と根拠を示してIntent改善を提案する。
既に必要な要件が明記されている場合は、その記載を根拠にIntent修正は不要と判断し、読込・適用や検証の問題を調べる。
Intentの不足とガードレールの問題が併存する場合も、一方の判断で他方の評価を省略しない。
これらの判断は既存の原因分析・改善案に含め、別の必須チェックリストや記録項目を設けない。
Intent改善も、上記の有限の反映対象・確認方法と下記の手動承認・改善の境界に従い、Audit中には適用しない。
Issue本文への反映は[Intentの記述](../../ai-driven-development/issue-guidelines.md#issue本文とコメントの責務)に従い、作業履歴を追加しない。

各指摘の対応は「今修正／変更不要／後日追跡」のいずれかとし、現在のIntent、観測事実・出典、
既存規則に加え、発生に必要な前提、通常運用でその前提が成立する蓋然性と根拠、発生時の影響を示して判断する。
理論上到達可能、または手動処理が並行可能という理由だけで修正必須にしない。
たとえば、正規migration経路外の管理操作を要する差分や、手動検証と再配信の重なりは、
通常運用でその条件が現実的に成立する根拠を確認して評価する。根拠がないことを発生不能や低頻度の証明にせず、未測定・未確認を明示する。
通常操作で再現する不具合や、Intent・既存要件が求める異常系の検証は、この基準によって除外しない。
重要度とは別に、対象PRのマージを妨げる問題かどうかとその根拠を明示する。
重要度だけで修正要否を決めず、後日追跡へ回したことだけでマージ可能と扱わない。
「今修正」は対応案であり、Audit中の実行許可ではない。変更不要でも、残るリスクや未確認事項、
コメント対応の要否を省かない。既存規則の読込・適用漏れへの対処と、規則自体の改善を区別する。

後日追跡には、対象IssueのURL、確認できる時点・前提・操作を含む確認条件、必要な証跡、完了条件を揃え、
そのIssueへ引き継ぐ内容を示す。証跡は確認に使うPR・対象commitやSHA・Actions run URLと結果など、
完了条件を判断できるものを指定する。追跡先や条件が未確定、Issueへの反映が未完了なら、残る作業として明示し、
引き継ぎ済みとは扱わない。引き継ぎの完了と実動確認の完了を区別し、未確認事項を会話だけに残さない。
コード変更がなくてもIssueへの追記が必要なら、変更対象にそのIssueと追記箇所・内容を含める。
目的・範囲・制約・完了条件の追加または変更を伴う場合はIntent改善として扱い、下記「手動承認」「改善」に従って反映する。
Issueの更新も既存の承認対象・権限の範囲で行い、追跡条件の提示だけから実行権限を推論しない。

再提示で対応、マージへの影響、変更対象、追跡条件の判断を変える場合は、変更した点と新たな根拠を示す。
根拠の追加と単なる表現変更を区別し、変わった提案・対象の承認は下記「手動承認」に従う。
これらは既存のAudit結果へ含め、別の出力形式、記録体系、承認段階を設けない。

具体的な改善が不要なら理由とコメント対応方針を報告し、改善を適用せず、[Coreの記録契約](../../ai-driven-development/aidd-checker.md#記録)に従って同じサイクルのAudit結果だけを更新し、分析を終了する。
返信・解決を提案した場合はその方針への手動承認を待ち、分析の終了をコメント対応完了と扱わない。
同じサイクルの追加指摘は既存PR・会話の出典を保持し、Auditファイルを最新の短い分析結果へ更新して、その対象への承認を取得する。別サイクルのAuditは上書きしない。試行ごとの分析履歴を本文へ積み上げない。
Audit結果、未解決の成果への修正、再利用可能な改善提案を分け、局所修正の許可を
ガードレール改善の許可へ転用しない。

### Audit結果の報告形式

報告形式の正本は本Policyとし、次の順序で提示する。工程記録の量・形式は
[Coreの記録契約](../../ai-driven-development/aidd-checker.md#記録)を維持し、報告のために新しい記録ファイル、操作履歴、ID体系を設けない。

1. **対象・結論**: 対象PR・指摘の範囲、分析の結論、マージへの影響と根拠を短く示す。
2. **一覧表**: 指摘ごとに次の列で判断と提案を示す。

   | No. | 判定・重要度 | 指摘と影響 | 直接修正 | 根本対策 | 反映先 | 検証方法 |
   | --- | ------------ | ---------- | -------- | -------- | ------ | -------- |

   No.は報告内の指摘と詳細・コメント対応を照合する番号とし、永続的なID体系にしない。
   判定・重要度には「今修正／変更不要／後日追跡」と重要度を分けて示す。
   指摘と影響には症状と成果への影響、直接修正には対象の不具合への対応案、根本対策には
   発生・見逃しの原因への対策案を示す。不要な対策は「不要」と理由、未確定な対策は
   「未確定」と不足する根拠を示し、空欄で判断を隠さない。
   反映先には変更するファイルと箇所（節・関数・行等）を示し、Issue更新が必要なら上記の
   後日追跡の条件に従って対象Issueと追記箇所・内容も含める。変更不要なら「該当なし」と理由を示す。
   検証方法には直接修正・根本対策や変更不要の判断を確認する具体的な方法を示し、
   実施済みの結果と提案・未実施を区別する。

3. **原因と根拠の詳細**: 一覧表のNo.に対応させ、症状、発生原因、見逃した理由を分け、
   観測事実・出典、判定理由、直接修正・根本対策との関係を示す。原因不明なら上記の根拠不足を示す。
   後日追跡の引き継ぎ内容・条件もここに示し、一覧表の提案との対応を保つ。
4. **コメント対応・未確認事項**: 対象PR・コメントURLと、threadがある場合はそのID・解決状態を特定し、
   コメントごとの判断理由と根拠、返信方針・返信する内容、Bot threadの解決条件、残る論点・作業を示す。
   返信・解決が不要な対象も理由を示し、変更不要という判断とコメント対応の完了を区別する。
   承認待ち・未実施・未確認の対象と、完了判断に不足する確認を示す。実行権限は下記「手動承認」に従う。

再提示・更新でもこの順序と列・項目の意味を維持し、同じ指摘のNo.と詳細・コメント対応の対応を保つ。
判断の変更は上記のとおり新たな根拠とともに示す。指摘なしでも同じ順序で、対象・結論には
確認した範囲と指摘なしの根拠、一覧表には同じ列で「該当なし」、原因と根拠の詳細には「該当なし」を示す。
コメント対応・未確認事項も省略せず、対象がなければ「該当なし」、残る未確認事項があればその内容を示す。

## 手動承認

提案、対象、検証方法をユーザーが確認できる形にして提示する。
改善を行う場合は、ユーザーがどの提案・対象を承認したかを、元の発言・Issue・PRの参照から確認し、必要な判断だけを短く要約する。承認eventは作らず、Audit結果には元の承認発言への参照だけを必要な範囲で残す。
提示済みの改善案・コメント対応方針に対する「Auditを承認します」は、その対象と内容の実行承認として扱い、追加の実行指示を要求しない。
変更不要の方針に含まれる理由返信・完了したBot threadの解決も同様に扱う。
変更要否だけへの承認から返信・解決権限を推論せず、返信のみ等の明示制限を優先する。方向性の指定だけは承認として扱わない。
開発の委任、Ship承認、Auditの依頼、agent自身の賛成、テストfixtureの承認は使用できない。
提案または対象が変わったら旧承認を流用しない。承認待ちは改善完了・サイクル完了ではない。

## 承認後のコメント対応

承認された対象・方針を引き継ぎ、[Git Workflow](git-workflow.md#prレビュー対応)に従って対応する。
変更不要なら判断理由と根拠を対象コメントへ返信する。返信・解決のために不要な変更、空コミット、
Task記録を作らず、提示した方針とユーザーの承認発言を根拠にする。
差分がある場合は必要な検証・commit・push・PRへの反映確認を終えてから完了の返信を行う。
指摘の投稿者がBotユーザーで、判断理由への返信と必要な作業が完了し、未解決の論点や競合コメントがなければ、返信後にthreadを解決する。
承認対象外には広げず、未完了threadは未解決のまま保持する。返信・解決・保留を対象ごとにread-backして報告し、投稿や解決の失敗・未確認を完了扱いしない。

## 改善

承認された提案を同じTaskの現在の採用判断で扱い、影響する旧証拠を再利用しない。
対象の正本・索引・検査・入口のうち必要な箇所だけを変更し、承認対象外へ広げない。
本文の追加より、既存の責務の明確化や不要な規則の削減が適切な場合もある。
Intentを変更する場合も承認された意味だけを反映し、元の出典と訂正履歴を残す。

改善の差分と承認範囲を照合したら、現在のIntentと改善済みガードレールを再確認してIntentへ戻る。
この境界で前サイクルを閉じ、同じTaskで設計・実装の要否を判断し、該当する検証・レビュー・Shipまで行う。次のAuditもユーザーの明示依頼で開始する。
改善の承認範囲は次サイクルでも維持する。Intentへの復帰だけで新しい作業権限を得たとは扱わない。
反映結果、検証結果、未達・未確認を示す。改善による成果は別事例や反例でも確認し、
一回の成功だけで一般的な品質向上を宣言しない。

ガードレール改善の対象がPRレビューコメントの場合も、上記「承認後のコメント対応」に従う。
改善後の検証・Shipで得た対応内容とcommitを返信の根拠にする。

## 検査と要約の限界

Go Coreは現在の差分・検証・stage・配信先と工程結果の鮮度・更新範囲を照合する。Audit結果は分析資料であり、次サイクルのIntent・指示・承認の台帳ではない。
ユーザー発言の真正性、承認対象と許可の意味はhostと担当agentが元の発言・Issue・PRから確認する。
要約やCoreの成功を人間の承認の代わりにせず、生出力を保存しない。
