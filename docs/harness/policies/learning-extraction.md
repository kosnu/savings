# Learning Extraction

学びとは、finding入力ゲートを通過したfindingについて、通常経路での到達可能性を確認し、学び対象となるものの再発させない対象、発生原因、対策候補を調査して選んだ改善です。findingの内容には、レビュー上の指摘、検証上の指摘、運用上の指摘、変更された制約などがあり得ますが、その内容だけで入力ゲートを通過したとは扱いません。findingやfinding内で提案された対策を、そのまま確定した学びとして扱いません。

## 整理先

- タスクコンテキストの追加・変更: 現在のタスク固有の意図、スコープ、制約、成功条件、監督観点、または新しい体験や価値を追加・変更する。AIDDでは対象Issue本文への具体的な変更案、AIDD対象外の保守作業ではその作業依頼への変更案として扱う
- ルール・ポリシーの追加・変更: 複数タスクへ適用する新しい判断基準、責務、禁止事項を追加するか、既存ルールの意味、適用範囲、責務を変更する
- 既存ルール・ポリシーのsharp化: 既存ルールの意味や適用範囲を変えず、正常パターン、責務、用語、判断境界を明確にして解釈の幅を狭める

改善を採用するfindingは、この3つから主な振り分け先を1つ選びます。タスクコンテキストが新規または変更されたルールへ依存する場合は、タスクコンテキストで体験、価値、スコープを定義し、継続的な判断原則は正本ルールを参照します。同じ内容を両方へ重複して記載しません。

選定した対策の所有先は、Learn skillやルール文書に限定しません。guardrailの実装、契約、検証機構、所有責務、workflowの実行機構、または実行環境の変更が最も再発を防ぐ場合は、現在のTask内のguardrail所有面と必要な結果を具体化します。product実装は既存Development Issueのタスクコンテキストへ具体化します。正本ルール・ポリシー・workflow文書自体の変更とは区別し、Learnがhandoffを生成することだけを理由に、一方を他方へ置き換えません。

## finding入力ゲート

学びとして処理するfinding候補は、次のいずれかを入力元とするものだけです。

- 今回のLearn対象として明示的に渡された、または選択されたPRレビューコメント
- このセッション内で実施したレビューの結果として出力されたfinding。セッション中に転記または議論したPRレビューコメントはこの入力元に含めず、PRレビューコメントとして扱う
- ユーザーがLearnへ追加するよう明示したfinding

PRレビューコメントは、そのコメントを含むreview threadが未解決の場合だけfinding候補とします。resolved thread内のコメントは、PRまたはコメントが明示されている場合もfinding候補から除外します。候補選択時は`reviewThreads.isResolved`を取得し、threadの解決状態を持たないcomment一覧だけで候補を確定しません。

PRが指定され、対象コメントが限定されていない場合は、そのPRでfindingを含むreview commentを今回のLearn対象として選択します。PRも対象コメントも指定されていない場合は、current branchに対応するopen PRをGitHub上の状態から確認します。open PRが1件なら、そのPRでfindingを含むreview commentを今回のLearn対象として選択します。open PRが0件ならPRレビューコメントを候補へ追加せず、他の入力元を処理します。複数件ならStopし、対象PRまたはreview commentの指定を求めます。レビュー概要や自動通知は、独立したfindingを含まない限りfinding候補へ追加しません。

それ以外のセッション内容をfinding候補へ自動追加しません。会話、調査メモ、検証出力、commandやtoolの失敗、実装上の気付き、AIの提案、棄却された代替案は、原因調査の根拠には利用できますが、このセッションのレビュー結果に含まれるか、ユーザーが明示的に追加しない限りfinding候補ではありません。

原因調査でより深い原因や広い対策を発見した場合は、入力ゲートを通過したfindingの原因または対策として保持します。それ自体を別findingとして自動追加しません。各findingには入力元を1つ記録し、入力元がないものは到達可能性判定や分類へ進めず候補から除きます。入力ゲートを通過するfindingが1件もない場合はStopします。

## 通常経路の適用判定

原因調査と3つの振り分けを行う前に、findingが通常経路上で発生したものか、通常経路外の状態でだけ成立するものかを判定します。

通常経路とは、findingが評価する成果物またはタスク状態へ至るために、タスクコンテキストと適用時点の正本ルール・契約が提供している経路です。経路には、適用ルールの選択・読込・適用、宣言された所有者による処理、必須検証による違反検知、実行環境の準備を含めます。外部から生じる入力や異常でも、適用する契約が所有者へ防御的な処理を要求している場合は通常経路の対象に含めます。

通常経路上で観測されたルールの選択・読込・適用漏れ、または必須検証の検出漏れは、原因調査の対象にします。実際の発生がなくても、具体的な入力・処理・責務の欠陥から失敗へ至る根拠があれば調査できます。ルール違反という結果だけで契約外と判断せず、一方で「Agentがルールを守らない可能性がある」という一般的な仮定だけでは、制御不全や追加検査の必要性を確定しません。

通常経路外の状態でだけ成立すると確認したfindingは、次のすべてを根拠で確認できる場合だけ学びから除外します。

- 非対応・廃止済み経路の意図的な利用、通常経路外からの改変、または必須の実行環境前提の破壊がなければ発生しない
- 適用ルールの選択・読込・適用と必須検証が機能する通常経路からは、同じ原因の失敗へ到達しない
- 契約外の状態に対する防御または検知を所有者へ要求する適用契約がない

除外は4つ目の振り分け先ではありません。通常経路外の状態であることを確認した後、既存のタスクコンテキスト、正本契約、ルール適用・検知の仕組みだけで到達不能と判断でき、通常経路、そのルール、仕組み、所有責務、実行環境のいずれも変更不要な場合に限る判定結果です。通常経路では成立しない仮定的な状態への懸念は除外できますが、仕組みが防止または検知できるという未確認の前提だけで除外しません。

発生率の低さ、断続性、timing依存だけを除外理由にしません。通常経路から到達可能なら原因調査の対象ですが、到達可能性だけでは変更の必要性を決めません。再現できないことだけを到達不能の根拠にしません。通常経路、適用契約、到達可能性が曖昧な場合は除外せず、不足する根拠または判断を示してStopします。

除外するfindingには、通常経路、その経路から到達不能であることを示す正本契約と実装・設定・検証の根拠、除外理由を記録します。除外を正当化するために今回固有のcaseや禁止事項を新しいルールとして追加しません。

## 原因調査と対策選定

Learnでは、通常経路から到達可能なfindingについて、振り分け前に次を行います。

1. 観測された失敗、明示された理由、提案された対策を分け、再発させない事象または破られた不変条件を定義する。
2. 関係する現行実装、既存ルール・契約、ルールの選択・適用・検知機構、責務境界、workflow、実行環境のうち、原因候補を区別するために必要な最小の根拠を調べる。症状が観測された場所と、根本原因または制御不全がある場所を分け、失敗を生む前提と、その前提を所有する本文・契約・実装を特定する。既存規則がある場合は、判断基準の不足と選択・読込・適用・検知の不全を根拠で区別する。
3. 下記の決定論的検出可否を評価したうえで、既存の責務分担を維持して追加変更しない選択肢に加え、原因となる前提を所有層で直接変更する案と、前提を維持して例外・補足・手続きを追加する案を比較する。各案について、何が解消され、どの原因や負担が残るかを具体例で示す。前提を維持する案では、その前提を残す必要性も示す。手段は、ルール・ポリシーの追加・変更・sharp化、仕組み・契約・検証・所有責務、実行環境・tooling・runtime設定から原因に応じて選ぶ。
4. 原因の解消範囲、再発範囲の広さ、注意喚起ではなく予防できる強さ、所有責務の適合、強制可能性、副作用、実装コストを比較し、改善効果が負担を上回る、原因層の最小の実用的な対策を選ぶ。例外や追加機構を設けたこと自体を改善とは扱わず、一律に禁止もしない。追加検査で正当な作業まで拒否しないか、Agentが担う意味判断を形式的な記録で代用していないかを確認する。
5. 変更を採用する場合は、選定対策の正本所有者と具体的な反映先を特定する。guardrailの実装、契約、workflowの実行機構、実行環境を変える対策は、局所ルールへ変換せず、現在のTask内のguardrail所有面へ振り分ける。product実装を変える対策は既存Development Issueへ渡す。正本ルール・ポリシー・workflow文書自体を変える対策は、分類原則に従ってルール・ポリシーの追加・変更またはsharp化へ振り分ける。反映では[現行仕様と履歴の責務](documentation-policy.md#現行仕様と履歴)に従い、原因を所有する正本を直接更新する。原因が契約・実装にある場合は文言の変更だけで完了にしない。

追加変更の必要性は、観測された失敗または具体的に示した欠陥、既存の責務・検証が不十分な理由、対策で改善できる範囲を根拠に判断します。Agentの任意の違反をすべて機械的に防ぐことを完了条件にしません。記録の欠落・遅延を、実際の許可や判断の欠如と同一視しません。既存の責務分担で十分な場合や、追加変更の利益が負担に見合わない場合は、理由を示して変更不要と結論できます。

findingに影響しない層まで一律に調査する必要はありません。ただし、選んだ原因と対策を有力な代替候補から区別できるだけの根拠を示します。

## 決定論的検出可否

通常経路から到達可能な各findingについて、同じ明示入力・状態・契約から、意味推論なしに同じ違反判定を得られるかを必ず評価します。再発回数を評価開始の条件にしません。判定に必要な外部情報や時刻がある場合は、それも入力として特定します。症状全体ではなく、原因経路のうち検出できる条件を対象にします。

| 判断         | 必要な根拠                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------ |
| 可能         | 観測できる入力、適用契約、違反条件、受け入れる正常例と拒否する違反例を示せる               |
| 部分的に可能 | 機械判定できる条件を上と同様に示し、残る意味判断とその担当者を分けられる                   |
| 不可         | どの判定が意図・設計・文脈の意味理解を必要とし、なぜ観測事実だけでは区別できないかを示せる |
| 根拠不足     | 可否を分ける入力・契約・観察が不足している。足りない根拠と、判断できる範囲を示す           |

根拠不足を不可や変更不要へ読み替えません。未確定部分に依存する対策の採否は保留し、独立して判断・実行できる許可済み部分は続行します。機械化可否と対策の採否は別です。可能でも既存の検査で十分な場合や追加コストが効果を上回る場合は、根拠を示して変更不要と結論できます。

機械化する場合は、違反条件を所有する既存の層を選びます。状態・参照・履歴の不変条件はchecker、pathからの適用漏れはrule-map、振る舞いの回帰はtestと必須verificationへの接続を候補にします。既に検出器があるなら、実行・routingの欠落を直せるか確認し、同じ検査を別の層へ複製しません。新しい注意書きで代用する案を選ぶ場合は、機械化を採用しない具体的な理由を残します。

例えば、存在しない検証case IDへの参照は機械判定できますが、そのcaseが要求を十分に検証するかは意味判断です。両者が混在するfindingは、参照の整合をchecker、検証内容の妥当性をagentのreviewへ分けます。文章の存在や「確認済み」の自己申告だけで意味判断を検出できたとは扱いません。機械化可能性の評価そのものもagentの判断であり、全findingをcheckerへ移すことは目標にしません。

## 対策の完了判断

担当agentは、選定時の具体例を更新後の本文・契約・実装へ当てはめ、失敗を生む前提がどう変わったか、何が解消され何が残るかを検証・レビューします。例外経路で症状を回避できたことや検査成功だけを、原因の解消の根拠にしません。前提を維持する対策も、残す理由と効果の範囲を確認して評価します。

検出機構を変更した場合は、対象の違反を検出する回帰caseと、同じ境界の正常入力を受け入れるcaseで確認します。検出器単体の成功に加え、対象変更から必要な検証が選ばれ実行される通常経路を確認します。採用した機械化が次のTaskでも働くための正本・routing・実行先と適用開始条件を示し、手動の任意実行だけで自動適用と結論しません。意味判断を残す場合は担当者とreview観点を検証へ接続します。文書上の判断基準だけを変える場合は、対照的な具体例によるreviewで確認でき、本文の文字列を照合するだけのテストを追加しません。

現在の正本と必要な参照先から適用すべき仕様を理解でき、無効な前提や重複説明を現行ルールとして読み合わせる必要がないことを確認します。原因・対策比較・検証結果はTask・Decision・Evidence等へ記録し、履歴を現行仕様の代用にしません。

根治と判断するのは、対象とした原因経路の解消を根拠で説明できる範囲です。残る原因や未検証部分は明示し、症状の緩和や部分的な改善を根治と言い換えません。すべての再発を防ぐ証明や意味判断の自動判定器は要求しません。

## 分類原則

- 現在または次のタスクに固有の情報、新しい体験や価値は、タスクコンテキストの追加・変更へ置きます。
- 複数タスクへ適用する新しい判断基準、または既存ルールの意味、適用範囲、責務を変える知見は、ルール・ポリシーの追加・変更へ置きます。
- 既存ルールの意図は正しいが解釈の幅や責務境界が曖昧な場合は、既存ルール・ポリシーのsharp化へ置きます。個別事例や禁止手段を列挙するのではなく、正常パターンと責務を直接明確にします。
- findingが既存ルールで対応済みでも、原因調査からそのルールの意味、適用範囲、責務、正常パターン、判断境界に不足があると確認できた場合だけ、そのルールを変更します。意味、適用範囲、責務を変える必要があれば追加・変更へ、意図を保ったまま原因となる曖昧さを解消できればsharp化へ置きます。
- 既存ルールが正しくても、通常経路でのルール選択・適用・検知、必要な強制、契約、責務の配置、または実行環境に具体的な原因があり、追加変更が必要と判断した場合は、ルールを増やさずに、その原因を所有するguardrail面へ振り分け、現在のTaskで扱います。適用対象のルールへ違反したという事実だけでは除外しません。新規ルールは、継続的な判断境界が欠け、そのルールが原因となる判断点へ作用できる場合に選びます。
- 複数の関連タスクへ適用するが、特定のプロダクト段階で失効する新しい制約は、ルール・ポリシーの追加・変更として期限付き監督ルールを追加します。適用対象、判断基準、失効条件、失効後に定義すべき体験または正本ルールを明記します。
- 期限を設けないルール・ポリシーには、現在の未対応を固定化せず、正常パターンと責務を直接定義します。
- 学びの根拠に将来の構想が含まれていても、対応する新規タスクや体験が定義されていない場合は、先回りして別タスクのタスクコンテキストを作りません。
- ユーザーが例示として示した語句や案は候補として保持し、明示的に採用されるまで確定したタスクコンテキストとして扱いません。
- 複数のfindingが同じ判断を更新する場合は、ユーザーまたは根拠となる確定ソースが採用を明示した後続の判断によって旧判断を置き換え、競合のない内容として、分類結果に応じた単一の反映先へ統合します。新旧の判断を併記してはいけません。
- 競合するfindingについて、ユーザーまたは根拠となる確定ソースが採用を明示していない場合は、いずれかを推測で採用せず、Stopして採用判断を確認します。
- ユーザーの指摘と理由を先に保持し、AIの解釈を分けます。解釈によって新しい可視情報、操作、制約、成功条件が増える場合は、推測せずStopします。

## 出力構造

各findingは、改善を採用する場合は`学び`、通常経路から到達不能と確認した場合は`除外`、既存責務や対策の費用対効果から追加変更を採用しない場合は`変更不要`として記録します。変更不要を正当化するために到達不能と扱いません。

記述量はfindingの重要度・複雑さと、判断を追跡するために必要な根拠に合わせます。以下は確認・保持する情報であり、項目ごとの見出しや長文の記入を必須にしません。単純なfindingは結論・理由・根拠参照を短くまとめ、同じ根拠や比較は参照で共有できます。原因が複合する場合や、責務・契約・許可境界を変える場合は、選定理由と残る影響を説明できるだけ具体化します。短縮のために入力元、必要な評価、反映先・検証との対応を失わせず、関係しない項目の穴埋めや同じ説明の転載は求めません。

学び対象には、指摘、入力元、通常経路、到達可能性の根拠、明示された理由、防ぐ再発、原因とその根拠、決定論的検出可否とその根拠、比較した対策と選定対策、振り分け、反映先、具体的な変更、後続の実行経路、必要な参照関係を記録します。検出可否の根拠には上記の入力・違反条件・正常例・残る意味判断を含め、機械化を採用しない場合はその理由を残します。

除外対象には、指摘、入力元、通常経路、到達不能を示す正本契約と実装・設定・検証の根拠、除外理由を記録します。

変更不要には、指摘、入力元、到達可能性の判断、既存の責務分担、具体的な原因の有無、決定論的検出可否とその根拠、比較した対策と採用しない理由を記録します。根拠不足は欠陥なしの証明とせず、不明点と判断できる範囲を明示します。

入力ゲートを通過したfindingを欠落させず、各findingの判断結果を1回だけ記録します。同じ内容を複数の振り分け先へ複製しません。
未確定のfindingは、不足する根拠・判断と保留範囲を示し、確定した結果と分けて残します。保留を除外・変更不要・完了へ読み替えません。

## 実行文脈

Learnはfeedbackの分析と改善であり、別Taskを必須にしません。単独依頼でもLearn用Issueは作成しません。
分析・分類の依頼だけでは反映を許可しません。明示的な更新依頼の範囲では、正本文書だけでなく
rule-map、checker、検証profile、adapter、実行機構と必要な回帰testをLearn内で更新できます。
これはproduct implementationの許可ではありません。

変更前にfeedback、authorization、有限の作業範囲を現在のTaskへ記録します。既存Taskがない単独依頼はLearn Taskを開始できます。
ユーザーの明示制限とagentの変更予定一覧を区別し、委任内の追加は
[作業範囲とguardrailの契約](../../ai-driven-development/workflow.md#rule--ownership--guardrail)に従います。
開始時のchecker binaryと旧policy/profileを維持して検証し、担当agent自身が最新差分と
checkpoint/evidenceをreviewして、依頼された許可範囲で確定します。変更後checkerの成功だけでは完了にしません。
独立reviewや別agentの呼び出しは必須にせず、ユーザーが明示的に依頼した場合だけ行います。
Coreの具体的な改訂・失効・検証境界は `docs/ai-driven-development/workflow.md` を適用します。

Development中のguardrail変更も、許可範囲で同じTaskのDecisionへ記録し、修正・検証して続行します。
作業種別の変化だけを理由に中断、独立Taskへの引渡し、ブランチ分割を要求しません。
新しいproduct intentが必要な場合は既存Issueへ明示反映し、実際の許可範囲を確認します。
分析結果の「反映」は指定済みの反映先だけを許可し、product実装や次cycle開始の許可へ拡張しません。

タスク固有のintentは既存Issueへ、再利用可能な判断・制御はguardrailへ置き、重複記載しません。
適格性確認、通常経路の適用判定、原因調査、対策比較、根拠の境界は引き続き適用します。

## 根拠の境界

前回実装コード、前回UI挙動、現在のdiff形状、前回実装固有の設計判断を、意図する挙動、タスクコンテキスト、ルールの正本にしません。一方で、発生原因の診断には、現行実装、設定、workflow、所有責務、検証結果、実行環境を根拠として利用します。実装やdiffから意図を逆算せず、元のIssueまたはタスクコンテキスト、明示的なフィードバック、既存の正本ルール、監督制約と分けて扱います。

## Stop条件

この文書のStopは、不足する根拠・判断に依存する分類、採用判断、変更または公開操作を保留することです。利用可能なrepository・契約・入力元の調査で解消できる不足は、まず担当agentが調べます。通常の技術判断は委任内で行い、未調査や未記入であることだけをユーザー確認の理由にしません。

調査後も次が残る場合は、該当する依存部分を保留し、不足点と成果への影響を示します。ユーザーにしか決められない意図・許可・採用判断や、提供が必要な情報を具体的に確認します。回答を待つ間も、独立した適格findingの分析と許可済みの変更・検証は続行します。全作業が依存する場合だけ全体を停止します。

- 入力元、通常経路、適用契約、到達可能性、再発対象または原因経路を特定できず、対象findingの評価を確定できない。
- 採用対策の振り分け、正本所有者、反映先、対象Issue、または期限付き監督ルールの適用範囲・失効条件を特定できず、その変更を安全に具体化できない。
- 意図や成功条件の不足、対策候補やfinding間の競合により、成果・スコープ・制約・権限・リスク・所有責務が変わり、既存の依頼と確定ソースから採用判断を選べない。前回実装から意図を逆算して補わない。
- 適用ルール間またはユーザー指示との矛盾を、既存の許可根拠と正本から解消できない。

対象PRが複数で一意に選べない場合は、そのPRコメントの選択を保留して対象を確認し、他の明示された入力元を処理します。入力ゲートを通過するfindingが1件もない場合は、その旨を報告してLearnの処理を終了します。これを理由に無関係なfindingを追加したり、独立した許可済み作業を止めたりしません。
