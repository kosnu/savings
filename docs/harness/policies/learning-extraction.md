# Learning Extraction

学びとは、finding入力ゲートを通過したfindingについて、通常経路での到達可能性を確認し、学び対象となるものの再発させない対象、発生原因、対策候補を調査して選んだ改善です。findingの内容には、レビュー上の指摘、検証上の指摘、運用上の指摘、変更された制約などがあり得ますが、その内容だけで入力ゲートを通過したとは扱いません。findingやfinding内で提案された対策を、そのまま確定した学びとして扱いません。

## 整理先

- タスクコンテキストの追加・変更: 現在のタスク固有の意図、スコープ、制約、成功条件、監督観点、または新しい体験や価値を追加・変更する。AIDDでは対象Issue本文への具体的な変更案、harness-taskでは次のInputとして扱う
- ルール・ポリシーの追加・変更: 複数タスクへ適用する新しい判断基準、責務、禁止事項を追加するか、既存ルールの意味、適用範囲、責務を変更する
- 既存ルール・ポリシーのsharp化: 既存ルールの意味や適用範囲を変えず、正常パターン、責務、用語、判断境界を明確にして解釈の幅を狭める

各findingは、この3つから主な振り分け先を1つ選びます。タスクコンテキストが新規または変更されたルールへ依存する場合は、タスクコンテキストで体験、価値、スコープを定義し、継続的な判断原則は正本ルールを参照します。同じ内容を両方へ重複して記載しません。

選定した対策の所有先は、Learn skillやルール文書に限定しません。実装、契約、検証機構、所有責務、workflowの実行機構、または実行環境の変更が最も再発を防ぐ場合は、その所有面と必要な結果をタスクコンテキストへ具体化します。正本ルール・ポリシー・workflow文書自体の変更とは区別し、Learnがhandoffを生成することだけを理由に、一方を他方へ置き換えません。

## finding入力ゲート

Learn skillまたはharness-taskで学びとして処理するfinding候補は、次のいずれかを入力元とするものだけです。

- 今回のLearn対象として明示的に渡された、または選択されたPRレビューコメント
- このセッション内で実施したレビューの結果として出力されたfinding。セッション中に転記または議論したPRレビューコメントはこの入力元に含めず、PRレビューコメントとして扱う
- ユーザーがLearnへ追加するよう明示したfinding

PRレビューコメントは、そのコメントを含むreview threadが未解決の場合だけfinding候補とします。resolved thread内のコメントは、PRまたはコメントが明示されている場合もfinding候補から除外します。候補選択時は`reviewThreads.isResolved`を取得し、threadの解決状態を持たないcomment一覧だけで候補を確定しません。

PRが指定され、対象コメントが限定されていない場合は、そのPRでfindingを含むreview commentを今回のLearn対象として選択します。PRも対象コメントも指定されていない場合は、current branchに対応するopen PRをGitHub上の状態から確認します。open PRが1件なら、そのPRでfindingを含むreview commentを今回のLearn対象として選択します。open PRが0件ならPRレビューコメントを候補へ追加せず、他の入力元を処理します。複数件ならStopし、対象PRまたはreview commentの指定を求めます。レビュー概要や自動通知は、独立したfindingを含まない限りfinding候補へ追加しません。

それ以外のセッション内容をfinding候補へ自動追加しません。会話、調査メモ、検証出力、commandやtoolの失敗、実装上の気付き、AIの提案、棄却された代替案は、原因調査の根拠には利用できますが、このセッションのレビュー結果に含まれるか、ユーザーが明示的に追加しない限りfinding候補ではありません。

原因調査でより深い原因や広い対策を発見した場合は、入力ゲートを通過したfindingの原因または対策として保持します。それ自体を別findingとして自動追加しません。各findingには入力元を1つ記録し、入力元がないものは到達可能性判定や分類へ進めず候補から除きます。入力ゲートを通過するfindingが1件もない場合はStopします。

## 通常経路の適用判定

原因調査と3つの振り分けを行う前に、findingが通常経路上で発生したものか、通常経路外の状態でだけ成立するものかを判定します。

通常経路とは、findingが評価する成果物またはタスク状態へ至るために、タスクコンテキストと適用時点の正本ルール・契約が提供している経路です。経路には、適用ルールの選択・読込・適用、宣言された所有者による処理、必須検証による違反検知、実行環境の準備を含めます。外部から生じる入力や異常でも、適用する契約が所有者へ防御的な処理を要求している場合は通常経路の対象に含めます。

通常経路上で、既存ルールが適用対象なのに選択・読込・適用されなかったfinding、またはその違反を必須検証が検知できなかったfindingは、通常経路を構成する仕組みまたは所有責務の制御不全として扱います。ルール違反という結果だけを根拠に、契約外の経路として除外してはいけません。ルールの選択・適用・検知を担う仕組みと責務が同じ原因の失敗を防止または検知できるかを調べます。

通常経路外の状態でだけ成立すると確認したfindingは、次のすべてを根拠で確認できる場合だけ学びから除外します。

- 非対応・廃止済み経路の意図的な利用、通常経路外からの改変、または必須の実行環境前提の破壊がなければ発生しない
- 適用ルールの選択・読込・適用と必須検証が機能する通常経路からは、同じ原因の失敗へ到達しない
- 契約外の状態に対する防御または検知を所有者へ要求する適用契約がない

除外は4つ目の振り分け先ではありません。通常経路外の状態であることを確認した後、既存のタスクコンテキスト、正本契約、ルール適用・検知の仕組みだけで到達不能と判断でき、通常経路、そのルール、仕組み、所有責務、実行環境のいずれも変更不要な場合に限る判定結果です。通常経路では成立しない仮定的な状態への懸念は除外できますが、仕組みが防止または検知できるという未確認の前提だけで除外しません。

発生率の低さ、断続性、timing依存だけを除外理由にしません。通常経路から到達可能なら学び対象です。再現できないことだけを到達不能の根拠にしません。通常経路、適用契約、到達可能性が曖昧な場合は除外せず、不足する根拠または判断を示してStopします。

除外するfindingには、通常経路、その経路から到達不能であることを示す正本契約と実装・設定・検証の根拠、除外理由を記録します。除外を正当化するために今回固有のcaseや禁止事項を新しいルールとして追加しません。

## 原因調査と対策選定

Learnでは、通常経路から到達可能なfindingについて、振り分け前に次を行います。

1. 観測された失敗、明示された理由、提案された対策を分け、再発させない事象または破られた不変条件を定義する。
2. 関係する現行実装、既存ルール・契約、ルールの選択・適用・検知機構、責務境界、workflow、実行環境のうち、原因候補を区別するために必要な最小の根拠を調べる。症状が観測された場所と、根本原因または制御不全がある場所を分ける。
3. 新規ルール・ポリシーの追加、既存ルール・ポリシーの変更またはsharp化、仕組み・契約・検証・所有責務の変更、実行環境・tooling・runtime設定の修正から、該当する対策候補を同列に比較する。
4. 再発範囲の広さ、注意喚起ではなく予防できる強さ、所有責務の適合、強制可能性、副作用、実装コストを比較し、原因層にある最小の実用的な対策のうち、最も再発を防げるものを選ぶ。
5. 選定対策の正本所有者と具体的な反映先を特定する。実装、契約、workflowの実行機構、実行環境を変える対策は、局所ルールへ変換せず、その所有面を対象とするタスクコンテキストへ振り分ける。正本ルール・ポリシー・workflow文書自体を変える対策は、分類原則に従ってルール・ポリシーの追加・変更またはsharp化へ振り分ける。

findingに影響しない層まで一律に調査する必要はありません。ただし、選んだ原因と対策を有力な代替候補から区別できるだけの根拠を示します。

## 分類原則

- 現在または次のタスクに固有の情報、新しい体験や価値は、タスクコンテキストの追加・変更へ置きます。
- 複数タスクへ適用する新しい判断基準、または既存ルールの意味、適用範囲、責務を変える知見は、ルール・ポリシーの追加・変更へ置きます。
- 既存ルールの意図は正しいが解釈の幅や責務境界が曖昧な場合は、既存ルール・ポリシーのsharp化へ置きます。個別事例や禁止手段を列挙するのではなく、正常パターンと責務を直接明確にします。
- findingが既存ルールで対応済みでも、原因調査からそのルールの意味、適用範囲、責務、正常パターン、判断境界に不足があると確認できた場合だけ、そのルールを変更します。意味、適用範囲、責務を変える必要があれば追加・変更へ、意図を保ったまま原因となる曖昧さを解消できればsharp化へ置きます。
- 既存ルールが正しくても、通常経路でのルール選択・適用・検知、必要な強制、契約、責務の配置、または実行環境が原因の場合は除外せず、ルールを増やさずに、その原因を所有するタスクコンテキストへ振り分けます。適用対象のルールへ違反したという事実だけでは除外しません。新規ルールは、継続的な判断境界が欠け、そのルールが原因となる判断点へ作用できる場合に選びます。
- 複数の関連タスクへ適用するが、特定のプロダクト段階で失効する新しい制約は、ルール・ポリシーの追加・変更として期限付き監督ルールを追加します。適用対象、判断基準、失効条件、失効後に定義すべき体験または正本ルールを明記します。
- 期限を設けないルール・ポリシーには、現在の未対応を固定化せず、正常パターンと責務を直接定義します。
- 学びの根拠に将来の構想が含まれていても、対応する新規タスクや体験が定義されていない場合は、先回りして別タスクのタスクコンテキストを作りません。
- ユーザーが例示として示した語句や案は候補として保持し、明示的に採用されるまで確定したタスクコンテキストとして扱いません。
- 複数のfindingが同じ判断を更新する場合は、ユーザーまたは根拠となる確定ソースが採用を明示した後続の判断によって旧判断を置き換え、競合のない内容として、分類結果に応じた単一の反映先へ統合します。新旧の判断を併記してはいけません。
- 競合するfindingについて、ユーザーまたは根拠となる確定ソースが採用を明示していない場合は、いずれかを推測で採用せず、Stopして採用判断を確認します。
- ユーザーの指摘と理由を先に保持し、AIの解釈を分けます。解釈によって新しい可視情報、操作、制約、成功条件が増える場合は、推測せずStopします。

## 出力構造

通常経路から到達可能なfindingは`学び`、到達不能なfindingは`除外`へ置き、findingごとに関係を保ちます。

学び対象には、指摘、入力元、通常経路、到達可能性の根拠、明示された理由、防ぐ再発、原因とその根拠、比較した対策と選定対策、振り分け、反映先、具体的な変更、後続の実行経路、必要な参照関係を記録します。

除外対象には、指摘、入力元、通常経路、到達不能を示す正本契約と実装・設定・検証の根拠、除外理由を記録します。

入力ゲートを通過したfindingを欠落させず、各findingを`学び`または`除外`の一方へ1回だけ記録します。同じ内容を複数の振り分け先へ複製しません。

## 実行文脈

- AI Driven Development: Ship完了後、または上流成果物の不足・誤り・矛盾によるサイクルStop後に、ユーザーがLearn skillを手動実行し、findingを3つの振り分け先へ整理する。正常系のBuild / VerifyとShipの間には挟まない。正本ルール・ポリシー・workflow文書の変更を選定した場合は、ユーザーが明示的に反映を指示した独立更新として完了し、その更新へ依存するタスクは完了後に新しいAIDDサイクルを開始する。実装、契約、検証機構、所有責務、workflowの実行機構、実行環境の変更を選定した場合は、対象Issue本文への具体的なTask Context変更案とし、Issueへ適用した後に新しいAIDDサイクルをRequirementsから開始する。Learnから後者の対象面を直接修正せず、PRDやDesign Docも直接変更しない。
- harness-task: finding入力ゲートを通過したfindingを、harness-taskのInputとなるタスクコンテキストの追加・変更、ルール・ポリシーの追加・変更、または既存ルール・ポリシーのsharp化へ整理する。レビュー結果や検証出力は、入力ゲートを通過するfindingの根拠として利用できますが、それ自体をfinding候補へ自動追加しません。明示されたスコープ内のルール・ポリシー更新はタスク内で実施できる。

Learn結果への後続指示で「反映する」「適用する」とだけ指定された場合は、直前に分類した反映先へ適用します。正本ルール・ポリシー・workflow文書の変更は、特定済みの正本反映先だけへ適用します。AIDDのTask Context変更は特定済みの対象Issue本文へ適用し、Issueを再取得して確認します。対象Issueが特定できない場合はStopします。タスクコンテキストへの反映をプロダクトコードの変更許可として扱わず、実装を伴う後続作業はユーザーが明示的に開始する新しいAIDDサイクルで行います。

Learn skillは学びの抽出と整理に特化した導線ですが、学び抽出を独占しません。`harness-task`も作業中に学びを抽出し、スコープ内のルール更新またはタスクコンテキストのhandoffを行えます。

通常タスクのレビューコメントでは、現在のタスクで必要な修正を先に判断します。学び抽出は必要な修正の代わりではなく、Build / Verify完了後であることだけを理由に修正をStopさせません。

## 根拠の境界

前回実装コード、前回UI挙動、現在のdiff形状、前回実装固有の設計判断を、意図する挙動、タスクコンテキスト、ルールの正本にしません。一方で、発生原因の診断には、現行実装、設定、workflow、所有責務、検証結果、実行環境を根拠として利用します。実装やdiffから意図を逆算せず、元のIssueまたはタスクコンテキスト、明示的なフィードバック、既存の正本ルール、監督制約と分けて扱います。

## Stop条件

- 学びの根拠が曖昧
- finding入力ゲートを通過する候補がない
- current branchに対応するopen PRが複数あり、対象PRを一意に特定できない
- 通常経路、適用契約、または到達可能性を利用可能な根拠から特定できない
- 3つの振り分け先から主な振り分けを決められない
- 反映先のタスクコンテキストまたは正本ルールが特定できない
- AIDDのTask Context変更を反映する対象Issueが特定できない
- 期限付き監督ルールの適用対象または失効条件が特定できない
- 再発させない対象または原因経路を利用可能な根拠から特定できない
- 有力な対策候補が拮抗し、選択によりスコープ、挙動、リスク、所有責務が変わるが、ユーザー判断がない
- 選定対策の正本所有者または具体的な反映先を特定できない
- 意図する挙動を説明するために前回実装固有の事実を正本化する必要がある
- 競合するfindingの採用判断が、ユーザーまたは根拠となる確定ソースによって明示されていない
- 選択したrule-mapサブグラフと矛盾する
