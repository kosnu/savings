# Auditとガードレール改善

[AIDD v4](../../ai-driven-development/workflow.md)のShip後の指摘分析を扱う。
Auditは分析であり、改善の実行権限ではない。旧Learnという一体の工程は使用しない。
作業過程全体の振り返りは、Merge / Close後の[Retrospective](retrospective.md)が扱う。

## Audit

AuditはShip後のユーザーの明示依頼で開始する。Ship直後の実行委任から自動で開始せず、後から届くPRレビューコメントをShip時点に存在したものとして扱わない。
再開時は同じTaskとPRから配信対象を確認し、その時点のレビュー指摘を取得する。指摘がない場合はその事実を報告し、作業過程の改善探索に切り替えない。

レビュー指摘や成果へのユーザーの訂正を、実際の記録に基づいて確認する。
指摘の原因を確かめるために関連する作業記録を参照できるが、進め方全体の改善探索へ広げない。
PR threadを入力にする場合はthreadごとの
解決状態とコメントを確認し、解決済みの問題を未解決扱いしない。
解決過程の一般化できる問題は、その解決状態と分析の目的を区別して扱える。

各改善候補には観測事実・出典、影響、原因または原因未確定、具体的改善案、有限の反映対象、
改善後の確認方法を示す。
方針不足、索引の到達性、読込・適用漏れ、検出漏れ、局所的な誤りを区別する。
既存規則があるだけで適用できたとは扱わず、推測した原因から禁止事項を増やさない。

Audit結果には変更・改善の要否に加え、対象PR・コメントURLと、threadがある場合はそのIDを特定し、
コメントごとの判断理由と根拠、返信する内容、Bot threadを解決する条件、残る論点・作業を示す。
返信・解決が不要な対象もその理由を示す。変更不要という判断とコメント対応の完了を区別する。
具体的な改善が不要なら理由とコメント対応方針を報告し、改善を適用せず、[Coreの記録契約](../../ai-driven-development/aidd-checker.md#記録)に従って同じサイクルのAudit結果だけを更新し、分析を終了する。
返信・解決を提案した場合はその方針への手動承認を待ち、分析の終了をコメント対応完了と扱わない。
同じサイクルの追加指摘は既存PR・会話の出典を保持し、Auditファイルを最新の短い分析結果へ更新して、その対象への承認を取得する。別サイクルのAuditは上書きしない。試行ごとの分析履歴を本文へ積み上げない。
Audit結果、未解決の成果への修正、再利用可能な改善提案を分け、局所修正の許可を
ガードレール改善の許可へ転用しない。

## 手動承認

提案、対象、検証方法をユーザーが確認できる形にして提示する。
改善を行う場合は、ユーザーがどの提案・対象を承認したかを、元の発言・Issue・PRの参照から確認し、必要な判断だけを短く要約する。承認eventは作らず、Audit結果には元の承認発言への参照だけを必要な範囲で残す。
提示済みの改善案・コメント対応方針に対する「Auditを承認します」は、その対象と内容の実行承認として扱い、追加の実行指示を要求しない。
変更不要の方針に含まれる理由返信・完了したBot threadの解決も同様に扱う。
変更要否だけへの承認から返信・解決権限を推論せず、返信のみ等の明示制限を優先する。方向性の指定だけは承認として扱わない。
開発の委任、Ship承認、Auditの依頼、agent自身の賛成、テストfixtureの承認は使用できない。
提案または対象が変わったら旧承認を流用しない。承認待ちは改善完了・サイクル完了ではない。

## 承認後のコメント対応

承認された対象・方針を引き継ぎ、[Git Workflow](git-workflow.md#prレビュー対応)に従って対応する。
変更不要なら判断理由と根拠を対象コメントへ返信する。返信・解決のために不要な変更、空コミット、
Task記録を作らず、提示した方針とユーザーの承認発言を根拠にする。
差分がある場合は必要な検証・commit・push・PRへの反映確認を終えてから完了の返信を行う。
指摘の投稿者がBotユーザーで、判断理由への返信と必要な作業が完了し、未解決の論点や競合コメントがなければ、返信後にthreadを解決する。
承認対象外には広げず、未完了threadは未解決のまま保持する。返信・解決・保留を対象ごとにread-backして報告し、投稿や解決の失敗・未確認を完了扱いしない。

## 改善

承認された提案を同じTaskの現在の採用判断で扱い、影響する旧証拠を再利用しない。
対象の正本・索引・検査・入口のうち必要な箇所だけを変更し、承認対象外へ広げない。
本文の追加より、既存の責務の明確化や不要な規則の削減が適切な場合もある。
Intentを変更する場合も承認された意味だけを反映し、元の出典と訂正履歴を残す。

改善の差分と承認範囲を照合したら、現在のIntentと改善済みガードレールを再確認してIntentへ戻る。
この境界で前サイクルを閉じ、同じTaskで設計・実装の要否を判断し、該当する検証・レビュー・Shipまで行う。次のAuditもユーザーの明示依頼で開始する。
改善の承認範囲は次サイクルでも維持する。Intentへの復帰だけで新しい作業権限を得たとは扱わない。
反映結果、検証結果、未達・未確認を示す。改善による成果は別事例や反例でも確認し、
一回の成功だけで一般的な品質向上を宣言しない。

ガードレール改善の対象がPRレビューコメントの場合も、上記「承認後のコメント対応」に従う。
改善後の検証・Shipで得た対応内容とcommitを返信の根拠にする。

## 検査と要約の限界

Go Coreは現在の差分・検証・stage・配信先と工程結果の鮮度・更新範囲を照合する。Audit結果は分析資料であり、次サイクルのIntent・指示・承認の台帳ではない。
ユーザー発言の真正性、承認対象と許可の意味はhostと担当agentが元の発言・Issue・PRから確認する。
要約やCoreの成功を人間の承認の代わりにせず、生出力を保存しない。
