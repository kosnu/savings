# Supabase設定変更のDev確認手順

機械的に判定できる項目はCIで確認し、運用上の判断とAPIで取得できない設定だけ人が確認する。
対象はDevとCI内の隔離Supabase。Prdには接続しない。
設定変更・DB適用・配信は[Devプレビュー運用](development-preview.md)に従う。

## 確認方法とタイミング

| 項目                    | 確認方法                                                                             | タイミング                                   |
| ----------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------- |
| 1. データ分離           | CI：全テーブル・列・RPCの正常／拒否試験とDev公開設定の照合                           | コード・DB・権限変更時                       |
| 2. セッション更新       | CI：更新後の認証・API利用                                                            | 認証関連の変更時                             |
| 3. Auth設定             | CI：取得できる設定と期待値の照合。人：期待値の決定、Googleログイン、取得できない設定 | 初回・関連設定変更時                         |
| 4. Web配信物の秘密情報  | CI：ビルド成果物とCloudflareのDev配信物を検査                                        | ビルド・配信ごと                             |
| 5. 公開・管理範囲       | CI：取得できる設定・権限と期待値の照合。人：必要な範囲の決定、取得できない設定       | 初回・関連設定変更時                         |
| 6. 支払いCRUDと予算履歴 | CI：合成データによる操作・集計・履歴の照合                                           | コード・DB変更時                             |
| 7. 取得上限             | CI：隔離Supabaseで上限超過時の取得・表示を試験                                       | 取得・集計処理・上限変更時                   |
| 8. 監視条件             | 人：確認先・担当・頻度・対応条件を決定                                               | 一度決定し、運用体制・基準変更時に見直す     |
| 9. 復元元・復旧範囲     | 人：利用できる復元元と復旧範囲を確認し、許容損失を合意                               | 一度確認し、設定・構成変更時に見直す         |
| 10. 切り戻し            | 人：対象変更に対応する手順と戻せる範囲を整備                                         | 対象変更ごとに一度。変更内容が変われば見直す |

以下のCI項目は実装すべき確認内容を示す。既存のDev CIはビルド・配信・DB適用までで、
全項目を自動検証しているわけではない。未実装の項目は未確認として扱う。

## CIで確認する内容

### 1. データ分離

CI内の隔離Supabaseで合成利用者A・Bを作り、互いのBookに所属しない状態で実APIを試験する。
管理用の資格情報は準備・後片付けに限り、境界試験は公開用キーと利用者トークンで実行する。

| 対象                                                    | 合格条件                                                                                                   |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| payments・categories・category_budgets・monthly_budgets | 本人が所属するBookの許可された操作は成功し、別Book・未認証の参照と変更は拒否される                         |
| users                                                   | 本人のプロフィールだけ参照でき、name・languageを更新できる。auth_user_idの変更は拒否される                 |
| books・book_members・category_pins                      | 本人のBook、本人の所属情報、本人のピンだけが返る。許可されていない変更は拒否される                         |
| 所有列・関連ID                                          | 別Bookへの付け替えや別Bookカテゴリへの関連付けが成立しない                                                 |
| 全公開RPC                                               | 許可された本人の操作は成功し、別利用者のデータを参照・変更できない。未認証での利用者データ操作は拒否される |

対象migrationの権限を期待値とし、新しい公開テーブル・列・RPCが増えたら試験対象に追加する。
対象漏れもCIで検出する。拒否はレスポンスだけでなく、所有者による再取得で変更がないことを判定する。
トークン切れ・不正な引数によるエラーを権限拒否の成功としない。

Devは設定の照合だけ行う。Data APIが有効で、Exposed schemasに`public`が選択され、
migration・権限・RLSが期待値と一致することを確認する。同じ拒否試験をDevで繰り返さない。

### 2. セッション更新

利用者のセッションを更新し、更新後のトークンで本人の取得・変更が成功することを自動判定する。
ブラウザの自動更新後も認証済み画面を操作できることは、ブラウザテストで確認する。
テスト用ログインを使った結果をGoogle OAuth経路の確認とは扱わない。

### 3. Auth設定

DevのManagement APIで取得できる次の設定を、事前に決めた期待値と比較する。

- Google providerの有効状態とDev用client ID
- Site URLとredirect allow list
- nonce、JWT期限、session/refresh設定
- Rate Limits・CAPTCHAの有効状態と値

期待値が未決定・取得権限が不足・APIで取得できない場合は合格にしない。
Google側の設定、ログインの実機確認と保護範囲の判断は下記の人による確認に残す。

### 4. Web配信物の秘密情報

ビルド済みのHTML・JSと、CloudflareのDev Previewから取得した配信物を検査する。
遅延ロードJSと公開source mapを含め、公開用キーだけが渡され、
Supabase管理token・secret/service_roleキー・Google client secretが含まれないことを確認する。
秘密値をCIログに出力しない。ビルドのみ成功した場合は実配信物の確認済みとしない。

### 5. 公開・管理範囲

DevのAPI・SQLから取得できる公開schema、テーブル・列・RPC権限、SSL Enforcement、
Network Restrictions、接続・pooler、Storage・Realtime・Functionsを期待値と照合する。
管理者role・MFA・管理tokenのscopeも取得可能な範囲で比較し、取得できない項目は人が確認する。
期待値を決める作業はCIでは代行しない。

### 6. 支払いCRUDと予算履歴

合成支払いの作成→金額・日付・カテゴリ変更→削除を行い、一覧・月次合計・カテゴリ集計・予算進捗を既知の期待値と照合する。
削除後に作成前の値へ戻り、現在月・過去月の予算が意図せず変わらないことを確認する。
APIの結果と、ブラウザでの表示をそれぞれ試験する。

### 7. 取得上限

Devの最大取得件数を読み取り、同じ上限・関連schema・権限・API構成のCI内隔離Supabaseで試験する。
上限+1件以上の合成データを用意し、一覧・集計・表示を既知の件数・総額と比較する。
全件取得・集計できるか、不完全な結果であることが画面に明示されれば合格とする。
共有Devの上限変更・大量投入・負荷試験は行わない。

## 人が確認・決定する内容

### 3・5. 認証と権限の採用判断

- Google providerは有効、Site URLはDevの代表Preview、redirect allow listは使用するPreviewの`/auth`を許可する。
- Google側のDev OAuth clientに`https://<Dev project ref>.supabase.co/auth/v1/callback`が登録されていることを確認し、DevでGoogleログインしてアプリへ戻れることを確認する。
- セッション設定の期待値、不正利用対策のGoogle経路への適用範囲・対象外の扱いを決める。
- 必要な公開schema・接続元・サービス・管理者role・token権限を決める。APIで取得できない実設定はDashboardで照合する。

初回と関連設定変更時に確認する。APIで取得できる設定を毎回人が読み直す手順にはしない。

### 8. 監視条件

Dev DashboardのLogs / Reports / Usageを確認先として、
Auth・Data APIのエラー、接続数、容量、MAU・egressについて次を決める。

- 確認担当
- 確認頻度
- 対応を始める条件
- 対応内容

これらが記載されれば完了。日々のエラー・容量の監視は、設定変更の検証とは別の運用作業とする。

### 9. 復元元・復旧範囲

DevのDatabase → Backupsと外部保管を確認し、次を記載する。

- 利用可能な復元元と取得方法
- DB・Auth・Storageのどこまで復旧できるか
- 復元できない範囲と、所有者が受け入れるデータ損失

復元元・復旧範囲を確認し、所有者の合意が得られれば完了。
設定・構成変更時に見直す。バックアップの定期実行・鮮度・失敗監視は別の運用作業とする。
復元試験が必要な場合は、合成データの復元元を隔離環境で使用する。

### 10. 切り戻し

対象変更ごとに次を記載する。

- 変更前の設定値と、戻すための操作
- DB変更があれば、対象index・policy・既存テーブルのACL・default privilegesを戻す方法
- 戻せる範囲と、元に戻せない・保証できない範囲

対象変更に対応する手順と範囲が明確になれば完了。継続監視の対象にはしない。
適用前ACLがなければ、anon/authenticatedへの再付与だけで完全復元と説明しない。
変更内容が変わったときに見直す。共有Devの復旧は[Devプレビュー運用](development-preview.md)に従う。

## 結果の記載

Issue・PRに「対象環境・commit／確認番号／期待結果／実結果／合格・不合格・未確認」を記載する。
CI結果と人の判断を区別し、未実装・未実施・取得不能・判断待ちを合格にしない。
トークン・秘密値を記載しない。
